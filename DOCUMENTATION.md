# Miles Man CRM — Documentation

A single-file CRM for a travel agency built around points/miles-based bookings, plus a public lead-intake form embedded on the agency's WordPress site.

- **CRM**: [index.html](index.html)
- **Public intake form**: [intake-form.html](intake-form.html) — embedded on `themilesman.com/book-a-trip-form/` via an `<iframe>`
- **Public credit card authorization upload**: [cc-auth-upload.html](cc-auth-upload.html) — a personalized per-client link (§4.12), not embedded anywhere

---

## 1. Architecture

- **Static, client-side only.** No backend server, no database. Both pages are self-contained HTML/CSS/JS files.
- **Hosting**: GitHub Pages, served from the `main` branch at `https://milesmaneric.github.io/milesman-crm/`.
- **Persistence**: the CRM's entire dataset lives in the browser's `localStorage` under the key `milesman_crm_v2`, as one JSON blob (`db = {clients, trips, vendors, planner}`). There is no server-side copy — the only durable backup is the Google Drive JSON export (see [§4.1](#41-google-drive-backup)).
- **Deploy process**: edit the file, commit, push to `main`. GitHub Pages auto-deploys. No build step.
  - Line endings must be `LF`, not `CRLF` (Windows editors default to CRLF — normalize before committing, e.g. `sed -i 's/\r$//' index.html`).
- **Standalone doc pages**: `documentation.html`/`user-guide.html` are static, styled HTML snapshots of this file and `USER_GUIDE.md`, generated by a `marked`-based Node script (not checked into this repo — lives outside the project folder) and opened via the sidebar's User Guide/Documentation buttons (`window.open('user-guide.html', ...)` / `window.open('documentation.html', ...)`). They are NOT auto-regenerated on every edit — re-run the generator and commit the refreshed `.html` files whenever `DOCUMENTATION.md`/`USER_GUIDE.md` changes meaningfully, or they'll drift out of date.
- **Mobile layout** (`@media(max-width:700px)` in `index.html`'s `<style>`): the sidebar becomes an off-canvas drawer, every `<table>` restacks into a card-per-row layout (`table,thead,tbody,th,td,tr{display:block}`) so ordinary data tables never need horizontal scrolling on a phone, and modals go full-screen. `#main` and `.email-preview` (the on-screen HTML preview used by Email Quote/Email Itinerary, which injects real `<table width="600">` email markup for cross-client-compatible rendering — see §3 Email) both carry an explicit `overflow-x:auto` (plus `-webkit-overflow-scrolling:touch` for iOS momentum scrolling) so that genuinely wide content — those fixed-pixel-width email tables being the main example — scrolls horizontally within its own box instead of being silently clipped off-screen with no way to see or reach it.
- **Money formatting**: every dollar amount displayed anywhere in the app goes through `money(n)` (`Number(n||0).toLocaleString(undefined,{minimumFractionDigits:2,maximumFractionDigits:2})`), always showing exactly 2 decimal places (`$1,234.00`, `$1,234.50`, never `$1,234`/`$1,234.5`). `fmt(n)` is the separate, decimal-free formatter (`Number(n||0).toLocaleString()`) reserved for whole counts like points/miles, where `.00` would be wrong — the two are intentionally never interchangeable.
- **Third-party services used**: Google Drive API (backup), Microsoft Graph API (Outlook email sync + auto-import), Mailchimp API (campaign activity sync), Anthropic API (in-app Assistant chat and the Reports page's AI Report tab, §3), WordPress.com API + the site's own public WordPress REST API (Analytics tab, §4.7/§4.9), Facebook Marketing API (Marketing tab, §4.8), X (Twitter) API v2 (Analytics tab, §4.10 — **the only paid, per-request-billed integration here**), TikTok Display API (Analytics tab, §4.11 — free, but gated behind TikTok's own App Review), submit-form.com (public form submission backend). API keys/secrets for Drive, Mailchimp, Anthropic, WordPress.com, Facebook, X, and TikTok are held server-side by a small proxy (`milesman-auth.vercel.app`, referenced in code as `DRIVE_AUTH_SERVER`/`WP_AUTH_SERVER`) since those APIs don't support CORS from a browser (or, for the site's own WordPress REST API, simply don't send CORS headers at all even though the data itself needs no auth — see §4.9). Outlook uses OAuth PKCE directly from the browser (no proxy needed — Microsoft's token endpoint supports CORS for SPAs).
  - The proxy's source lives locally at `C:\Users\ericl\milesman-auth-fix` (not a git repo — deployed straight to Vercel via `vercel --prod` from that folder, project name `milesman-auth`). Ten endpoints: `api/token.js` (Microsoft), `api/drive-token.js` (Google Drive token exchange/refresh, holds `GOOGLE_CLIENT_SECRET`), `api/mailchimp.js` (holds `MAILCHIMP_API_KEY`), `api/claude-messages.js` (holds `ANTHROPIC_API_KEY`, relays a conversation to Claude — used by both the Assistant widget and the Reports page's AI Report tab, never touches CRM data itself, all tool execution/data access happens client-side), `api/wordpress-token.js` (WordPress.com OAuth code exchange, holds `WORDPRESS_CLIENT_SECRET`), `api/wordpress-stats.js` (CORS relay for WordPress.com's stats API, §4.7), `api/wordpress-site-rest.js` (CORS relay for the site's own public `/wp-json/` REST API — no secret involved, §4.9), `api/facebook-token.js` (Facebook OAuth code exchange, holds `FACEBOOK_CLIENT_SECRET`), `api/facebook-graph.js` (CORS relay for Graph API calls, §4.8) — plus `api/secure-sync.js`, see §4.1a. **Four more are needed but not yet deployed**: `api/x.js` (§4.10 — one merged file covering both the OAuth token exchange and the API relay, not two, since this project is on Vercel's Hobby plan and already sits at its 12-Serverless-Function-per-deployment cap; see that section for the required `vercel.json` rewrite), `api/tiktok-token.js`/`api/tiktok-api.js` (§4.11 — will need the same treatment merged into one file once adding both would tip back over the cap), and `api/cc-auth-upload.js` (§4.12) — all are checked into the milesman-crm repo at `vercel-endpoints/` ready to copy into this project, since X analytics, TikTok analytics, and the credit card authorization upload can't work until they exist here. Unlike the other four, `api/cc-auth-upload.js` needs no new env vars — it reuses `GOOGLE_CLIENT_SECRET`/`DRIVE_SERVER_REFRESH_TOKEN`, already set for Secure Sync (§4.1a). `api/claude-messages.js` just forwards whatever `messages`/`system`/`tools` the browser sends — it doesn't force `tool_choice`, so a caller that wants a guaranteed structured response (like AI Report's single `generate_report` tool) relies on a system prompt instructing the model to always call that tool rather than reply in plain text.
- **Password gate**: the app is wrapped in `bootApp()`, which only runs after a client-side password screen is passed (or immediately, if `localStorage['mm_authed']==='1'` from a prior unlock on that device). The password itself is never hardcoded — first use on a device prompts to set one, and only a per-device salted SHA-256 hash (`mm_auth_hash`/`mm_auth_salt`) is stored, never transmitted anywhere. **This is explicitly not real security** — the repo is public, so both the check's logic and the `localStorage` data it's guarding are readable by anyone who looks at the source or opens dev tools; it only stops a casual visitor who stumbles on the GitHub Pages URL from seeing client data at a glance. See §4.1a (Secure Sync) for the one path that does have real server-side verification. Sidebar controls: **Lock** (clears `mm_authed`, re-prompts), **Close** (`closeApp()` — `saveDB()`, then a best-effort silent Drive backup via `runAutoDriveBackup()`, then `lockApp()`; must be defined inside `bootApp()`'s scope rather than alongside `lockApp()`/`unlockApp()` at the outer scope, since it calls `saveDB`/`runAutoDriveBackup`/`debugLog` — all local to `bootApp()`), **Change Password** (requires the current password), and a **Forgot password?** link on the login screen (resets just the gate, never touches CRM data, after a confirm).
- **Searchable selects**: every `<select>` that picks a client or a trip by name (Add/Edit Trip's Client, Email Quote's Client, Email Itinerary's Client and its client-dependent Trip, the Email page's mail-merge Client, the Task form's Linked Client/Linked Trip, and the Reports page's three Client filters) is wrapped with `searchableSelectWrap(selectHtml, placeholder)` — a type-to-filter text input laid over the real `<select>` (still in the DOM, just `display:none`, and still the single source of truth for every existing `gv()`/`getElementById(id).value` read and `'change'` listener elsewhere, so wrapping a select never requires touching the code that reads it). One delegated listener set, `bindSearchableSelects()`, bound once at boot (`bindClick`-style), drives every instance present or future — `ssRenderDropdown()` splits the typed query into words and requires every word to appear somewhere in an `<option>`'s text (not the query as one whole substring), specifically so a name typed in natural "First Last" order still matches an option stored "Last, First" (every client/vendor name goes through `toLastFirst()` — see §2 — so a plain whole-string substring match would silently hide someone whose name you typed the normal way); clicking or Enter sets the real select's value and dispatches a real `change` event, Escape/blur closes and reverts unsaved typing back to the actual selection. A select whose options get rebuilt programmatically after the initial render (e.g. Email Itinerary's Trip list, which depends on which client is picked) needs one added line, `resetSearchableSelectInput(selectId)`, right after the `.innerHTML=` rebuild, so the visible search text doesn't go stale against the freshly-reset selection.
- **Modals never close on an outside click.** Every popup (`$('modal').innerHTML=...` + `$('overlay').classList.add('open')`) only closes via its own explicit close control (`closeModal()`, wired to an X button/Cancel/Save). Clicking the dimmed backdrop is a deliberate no-op — it used to call `closeModal()` (`$('overlay').addEventListener('click', ...)` checking `e.target===$('overlay')`), which silently discarded any unsaved edits in the open form; that listener was removed rather than kept as a guarded/confirm-first close, since a modal never holds anything the user didn't just start typing.

## 2. Data Model

`db` has four top-level arrays, each with a human-readable ID prefix (`newId('C', db.clients)` etc.):

### `db.clients` (`C001`, `C002`, ...)
Core identity: `name` (stored "Last, First"), `email`, `phone`, `streetAddress`, `city`, `state`, `zip`, `birthdate`, `countryOfCitizenship`, `countryOfBirth`.

Lead source: `referredBy`, `referredByDetail`.

Preferences: `preferredAirline`, `preferredHotel`, `preferredCruiseLine`.

Loyalty balances: `mileageBalances` (airlines), `hotelBalances`, `cruiseBalances`, `carRentalBalances` are each an object keyed by brand name → `{balance, status}`; `creditCardBalances` is keyed by card name → a plain number (credit cards have no status tier).

Each of these renders via `balanceGrid()` as a collapsible section — collapsed by default unconditionally, even one that already has a nonzero balance/status set, so opening either form never presents a wall of fields regardless of how much data the client already has on file. The collapse state itself isn't persisted (it's just a `display:none` toggle on the grid div, driven by a click on the section's `<label class="balance-grid-toggle">`); a single delegated click listener, `bindBalanceGridToggles()`, is bound once per form open (both the client form and the trip form use `balanceGrid()` — the trip form's copy, in `tripBalanceSectionsHtml()`, mirrors the linked client's balances) rather than per-toggle, since the trip form's balance grids get replaced wholesale when its Client dropdown changes. This doesn't extend to the trip form's separate **Booked Trip Details** section — see §2's `booked` field for that section's own (also collapsed-by-default) category toggles.

**Bound exactly once per modal "session," guarded by `modal.dataset.balanceTogglesBound`** — without it, re-opening the form would stack another listener onto the persistent `$('modal')` element every time, and N stacked listeners toggle a section N times per click (an even N cancels itself out — click does nothing, which is indistinguishable from "broken"). `openTripForm()` deliberately clears that flag every time it renders (its balance grids get rebuilt fresh, tied to whichever client is now selected, so the old listener genuinely needs replacing). `openTaskForm()` used to clear the same flag too, despite the Task form never containing a single balance grid — harmless-looking, since a form with nothing to rebind just left the flag falsely cleared, until whichever Client form opened *next* saw an unset flag and bound a second, redundant listener on top of the one still attached from before. The intermittent, session-history-dependent "expanding a balance section on a client record sometimes doesn't work" bug was exactly this — it only showed up once a Task form had been opened at some point earlier in the session. Fixed by simply not touching the flag in `openTaskForm()` at all.

Branded credit card checklists: `airlineCreditCards`, `hotelCreditCards` are each a plain array of held card name strings (e.g. `['United Explorer Card','Marriott Bonvoy Boundless']`) — a simple has/doesn't-have checkbox list, unrelated to the loyalty balances above (no balance or status per card, and a different, narrower list of cards than `CREDIT_CARDS`/`creditCardBalances` — `AIRLINE_CREDIT_CARDS`/`HOTEL_CREDIT_CARDS` are specifically real airline- or hotel-branded co-brand cards, grouped by airline/hotel brand, keyed only for brands that actually have such a card — e.g. Four Seasons has no co-branded card, and Ritz-Carlton/W Hotels/Kimpton/Conrad share their parent brand's own program (Marriott/IHG/Hilton) rather than getting a separate entry). Rendered by the shared `brandedCardsChecklist()`/`readCardChecklist()` helpers (`index.html`) and mirrored on the public intake form and its importer (§5) via the matching `brandedCcChecklistHtml()` in `intake-form.html`. `brandedCardsChecklist()` collapses the same way `balanceGrid()` does above (same `.balance-grid-toggle` markup and the same delegated `bindBalanceGridToggles()` listener) — it used to render fully expanded with no toggle at all, which read as "the credit card sections don't collapse" since Credit Card Point Balances (a `balanceGrid()`, right above these two) did collapse. The one difference: since this list isn't a CSS grid, its toggle carries `data-open-display="block"` so the shared handler doesn't switch it to `display:grid` on expand.

Flags: `isPayingClient`, `isSubscriber` (both toggleable inline from the Clients table).

`discounts` — array of independently-checked discount type strings (`DISCOUNT_TYPES=['Military','AAA','First Responder','Educator']`, plus `'Other'`); `discountOther` holds the free-text detail when `'Other'` is checked. Unlike the fixed-choice Referred By select above, discounts are genuinely independent (a client can be both Military and AAA), so this is a checkbox list, not a select — rendered/read via `discountsFieldHtml()`/`readDiscounts()`/`bindDiscountOtherToggle()` (`index.html`), the same idPrefix-per-form pattern as the balance grids (`'fdis'` on the client form, `'tdis'` on the trip form — trips carry their own independent `discounts`/`discountOther`, since a discount can apply to one trip and not another even for the same client). Mirrored on the public intake form's Discounts section and its importer (§5) via individual `Discount - <type>` checkboxes plus `Discount - Other`/`Discount - Other Detail`, the same "one checkbox per name" convention as the form's `Need - <type>` travel-needs checkboxes.

`interests` — same shape as `discounts` (`INTEREST_TYPES=['Beach','Skiing','Boating','Fishing','Snorkeling','Horseback Riding','Adventure']`, plus `'Other'`/`interestOther`), on both client and trip records, via `interestsFieldHtml()`/`readInterests()`/`bindInterestOtherToggle()` (`'fint'`/`'tint'` idPrefixes). The importer's checkbox-list reader was generalized into one `extractChecklistWithOther(types, prefix)` inside `processTripFormRow()` rather than duplicating `extractDiscounts()`, since Discounts and Interests are the same shape end to end — both are also handled by the plain `mergeCardChecklist()` union-merge in the client-enrich branch (see the balance-merge note below for why a checklist union, not a differs-then-replace comparison, is the right merge for this shape: an unrepeated checkbox on a later submission means "not repeated here," not "no longer true").

Other: `notesLog` (array of `{ts, text, noteType, source?, msgId?, mcKey?}` — the activity timeline), `attachments`, `joined`, `totalTrips`.

`referralCredits` — array of `{referredName, date, amount, used, certNumber}`, shown/edited in a "Referral Credits" section on the client form (name, date, $ amount, a "Used" checkbox, delete button, "+ Add Referral Credit" for a manual row). `certNumber` is shown as a small read-only `#000123` badge — it's system-assigned (see §3 Email's certificate mechanics) and only present on rows created by actually sending the certificate email; a manually-added row has no certificate and no number. Sending the "Referral Credit Earned" email template (§3 Email) auto-appends one row per referred person to each selected referrer's record — see §3 Email for the multi-referrer/referred mechanics.

### `db.trips` (`T001`, `T002`, ...)
`clientId`/`clientName` = primary/billing contact. `clientIds` = array of additional linked client IDs (companions on a shared trip — a trip shows up on every linked client's record, not just the primary contact's).

`linkedTripIds` = array of other trip IDs that are part of the same overall vacation (e.g. a NYC leg + a Paris leg booked as two separate trip records) — distinct from `clientIds` above, which links *people* to one trip, not trips to each other. The Add/Edit Trip form's **Linked Trips** checkbox list is kept symmetric by `saveTrip()`: checking another trip there adds this trip's ID to *that* trip's `linkedTripIds` too, and unchecking removes it from both sides, so the link is never one-directional. The sync diffs against the trip's `linkedTripIds` as it was *before* this save (captured as `oldLinkedTripIds` before `db.trips` gets overwritten) against the freshly-read checkbox state, then walks every other trip in `db.trips` adding/removing this trip's ID accordingly. Since this is a checkbox list rather than a `<select>`, it isn't one of the `searchableSelectWrap()` instances (§1) — instead a plain `#trip-link-search` text input above the list (only rendered when there's at least one other trip to link) filters the `.trip-link-row` labels live via `input`, matching against each row's own `data-search` attribute (the same lowercased label text already shown) and toggling `display:none`/`flex` — checked state on a hidden row is untouched, so filtering never loses a selection.

**Saving a non-blank `booked.tripName` propagates it to every trip in the same linked group** — not just this trip's own direct `linkedTripIds`, but the whole connected component via `tripLinkGroups()` (called fresh after the symmetric-link sync above, so it reflects any linking/unlinking that just happened in this same save), so a 3-leg group linked in a star pattern (leg A linked to B and to C, but B/C never directly linked to each other) still gets one consistent name across all three. A blank Trip Name is never propagated — clearing this trip's own name doesn't erase a name already set on the others. This keeps the Trips page's group summary line (§3) showing one shared name rather than every distinct name found joined with `/`.

`origin`, `destination`, `departDate`, `returnDate`, `status` (`STATUSES` — Planning / Confirmed / Upcoming / In Progress / Completed / Cancelled; note `displayStatus()` separately *derives* a display-only "Upcoming" when a trip is still marked Completed but its `departDate` hasn't arrived yet — that's a different mechanism from the stored `Upcoming` status a user picks explicitly, see §3's Trips section), `type` (Leisure/Business/Honeymoon/Family/Adventure), `airline`, `flightClass`, `hotel`, `hotelNights`, `cruiseLine`, `shipName`, `pointsUsed`, `cashPaid`, `totalValue`, `bookingRef` (labeled **Invoice Number** in the Add/Edit Trip form — the property name itself is unchanged, since it's already relied on elsewhere as the invoice-report grouping key whenever a trip has no separate `invoiceNum`, §4), `invoiceDate`, `product`, `supplierId`/`supplierName`, `notes` (freeform — most intake-form fields that don't have a dedicated column end up compiled here as `Label: value` lines).

`invoiceDate` is a separate concept from `departDate` — `departDate` prioritizes the *travel* date (Ship Date on a revenue import) when one exists, while `invoiceDate` is the actual transaction/booking date from the source file's own "Date" column. The two can legitimately differ (booked one month, travel happens the next), which is why the "By Invoice #" report (§3) lets you choose which one to filter by. Only the revenue importer populates it automatically; it's also editable by hand on the Add/Edit Trip form for any trip.

`invoiceDate` didn't exist before this field was added, so trips imported before then have no value for it at all — re-running the exact same revenue import backfills it onto the matching existing trip (`finalizeImport()`'s duplicate-detection branch), the same way it already backfilled a supplier that was added to the Suppliers list after a trip's first import. Re-importing never creates a duplicate trip; it only fills in whatever the existing trip is still missing (supplier link and/or `invoiceDate`).

These top-level fields are the at-a-glance summary used by the Trips list, Calendar, Dashboard, and CSV exports — they stay populated exactly as before and nothing else had to change when `booked` (below) was added.

`clientName` is a denormalized copy of the primary client's `name` at save time, not a live lookup — every list/report that shows a trip's client reads this field directly rather than joining against `db.clients`. `saveClient()` propagates a name change onto every trip's `clientName` where `clientId` matches (`db.trips.map(t => t.clientId===id ? {...t, clientName:name} : t)`), so renaming a client updates the Dashboard/Trips page/reports immediately — before this sync existed, a rename only ever took effect on the Clients page itself, which is the only view that reads `client.name` live.

`booked` — the **Booked Trip Details** section (Add/Edit Trip modal), a confirmed-booking recap organized into the same categories as the intake form's "Type of Travel Needed" checkboxes, each with its own confirmation number and its own `price` (a plain dollar amount, separate from the trip's top-level `totalValue`/`cashPaid` — lets a trip's cost be broken down by category, e.g. $2,000 for the flight vs. $500 for the tour). `booked.tripName` is a section-level field (not per-category) for a human-friendly label like "Smith Family Alaska Cruise" — purely cosmetic, used only to personalize the Email Itinerary's opening line (falls back to the trip's `destination` when blank), not referenced anywhere else. Each of the 9 categories below is collapsed by default (`bookedCatSectionHtml()`, same `!==false`-means-collapsed pattern as `window._tripGroupsCollapsed`/`window._bookmarkCategoriesCollapsed`, tracked in `window._bookedCatCollapsed` keyed by category — Trip Name and the Summary block at the very end aren't part of any category and always stay visible) — click a category's heading to expand it. Note this is **only** the internal Add/Edit Trip modal's own categories; it's unrelated to and doesn't affect the public-facing `intake-form.html` ("the Book a Trip form" clients submit themselves, §4.4), which has no collapse behavior:
- `booked.airline` — `{records: [...]}`, an **array** of Airline Records (`airlineRecordRowInnerHtml()`/`readAirlineRecords()`) — one per confirmation/PNR, since a trip's air travel doesn't always fall under a single booking (e.g. two passengers on an award-ticket record, two more on a separate revenue-fare record for the same trip). Each record is `{recordNumber, nonStop (Yes/No), price, numPassengers (1-9, dropdown), passengerClientIds (array of client IDs, from a multi-select listing every client — `airPaxClientOptionsHtml()`), notes, pts (see below), segments}`, where `segments` is itself an **array** of flight-leg entries (a connecting or round-trip itinerary is more than one leg per record), each `{airline, flightNumber, origin, destination, departDate, departTime, arrivalTime, classOfService}`. Record Number, the points redemption blocks, Price, Number of Passengers, Passengers, and Notes are scoped to that one record (one PNR/one price/one note per record) rather than the whole Airline section or varying per segment.
  - Each record's own `numPassengers` and `passengerClientIds.length` are kept in sync two ways: a live warning (`updateAirlineRecordPaxWarning()`, fires on `change` of either field, scoped to that one record) that doesn't block anything, and a hard check in `saveTrip()` that walks every record independently and refuses to save (toast error naming which record, e.g. "Airline Record 2") if any record's counts don't match — only enforced when that record's `numPassengers` is actually set.
  - **Migration from the pre-records shape**: an old trip's `booked.airline` used to be one flat object (`confirmationNumber`/`nonStop`/`price`/`numPassengers`/`passengerClientIds`/`notes`/`segments`/`pts` directly on `air`, no `records` array, and before that, a single flight's `airline`/`classOfService`/`origin`/`destination`/`departDate` plus a `returnDate` directly on `air`, predating even `segments`). `bookedTripDetailsHtml()` detects a missing/empty `records` array and wraps whatever old-shape data exists into a single-entry `records` list (with the pre-`segments` single-flight shape further unwrapped into a 1-2 entry `segments` list first, the return leg becoming a second entry with origin/destination swapped) — old trips open and re-save cleanly with no explicit migration step required.
- `booked.hotel` — an **array** of hotel-stay entries (a trip can have multiple hotels), each `{hotelBrand, confirmationNumber, checkInDate, nights, price, notes, pts}` — already had its own per-entry `price` before this round of categories got one; `notes` is per-entry too, not shared across hotel stays. Unlike every other section below, `pts` (see below) lives **per hotel entry** rather than once for the whole section — each hotel stay already has its own confirmation number/price/notes, so its points redemptions are scoped the same way (a redemption is tied to one specific stay, not the whole trip's hotel booking as a unit). An old entry's single `program`/`amount` pair (the shape before this became a list) still loads fine, wrapped into a one-row `pts` list.
- `booked.cruise` — `confirmationNumber`, `cruiseLine`, `shipName`, `sailingDate`, `returnDate`, `nights`, `departurePort`, `returnPort`, `loyaltyNumber`, `price`, `notes`, `pts` (see below), and `cabins`: an **array** of cabin entries (a booking can cover more than one cabin on the same sailing), each `{cabinType, peopleInCabin, cabinNumber}` — same dynamic add/remove pattern as `booked.hotel`/`booked.tours`; an old trip's single `cabinType`/`peopleInCabin` shape (with no `cabinNumber` at all) still loads fine as a one-entry list. Cabin Type options come from `getQuoteConfig(cruiseLine).cabinTypes` (the same config Email Quote uses), so every cabin row is rebuilt whenever Cruise Line changes.
- `booked.carRental` — `confirmationNumber`, `company`, `carSize`, `pickupLocation`, `dropoffLocation`, `pickupDate`, `dropoffDate`, `pickupTime`, `dropoffTime`, `price`, `notes`, `pts` (see below)
- `booked.transfers` — an **array** of transfer / car-service ride entries (a trip usually needs several — airport pickup, hotel-to-restaurant, day trip), each `{pickupDate, pickupTime, origin, destination, carType, provider, confirmationNumber, price, notes}`. `carType` is `Car / SUV / Van / Any` (`TRANSFER_CAR_TYPES`, deliberately coarser than `CAR_SIZES` for self-drive rentals). Same dynamic add/remove pattern as `booked.hotel`/`booked.tours`; a trip saved before this category has no `transfers` key and reads as `[]`. Its Points Used and Insurance Premium/Coverage live in sibling top-level fields `booked.transfersPts` / `booked.transfersInsurancePremium` / `booked.transfersInsuranceCoverage` (same reason as `booked.toursPts` — `transfers` is a plain array). In the Email Itinerary each ride renders as its own "Transfer 1"/"Transfer 2" box (Pickup, From, To, Car Type, Provider, Confirmation Number).
- `booked.tours` — an **array** of tour entries (a trip can book more than one tour/activity), each `{confirmationNumber, vendor, description, price}` — same dynamic add/remove pattern as `booked.hotel`, an old single-object shape gets wrapped into a one-entry list. `vendor` is a dropdown (`TOUR_VENDORS` = every `CRUISE_LINES` entry plus Tauck/Viator/Get Your Guide — a booked tour is often a cruise-line shore excursion), not free text. No separate `notes` field here — `description` already serves that purpose per tour. Its Points Used entries live in a sibling top-level field, `booked.toursPts` (see below), rather than nested under `booked.tours` — `tours` is a plain array with no wrapping object to hang a `.pts` property off of, and `JSON.stringify` would silently drop a non-index property added directly to an array.
- `booked.themePark` — `confirmationNumber`, `park`, `ticketType`, `price`, `notes`, `pts` (see below)
- `booked.train` — `confirmationNumber`, `departureCity`, `arrivalCity`, `departureDate`, `returnDate`, `classOfService`, `price`, `logoUrl` (optional, plain text — see below), `notes`, `pts` (see below)
- `booked.bus` — same shape as `booked.train`: `confirmationNumber`, `departureCity`, `arrivalCity`, `departureDate`, `returnDate`, `classOfService`, `price`, `logoUrl`, `notes`, `pts` (see below)

**`pts`** — every Booked Trip Details section has its own "Points Used" block: a dynamic, add/remove-any-number-of-rows list of miles/points redemptions, each `{program, amount, cost}` — `program` is picked from a combined list of all airlines, hotels, and credit cards (a booking often mixes airline miles with a transferred credit-card-points balance), `amount` is points/miles used, `cost` is the cash paid alongside them (e.g. taxes/fees). Empty rows are filtered out on save, not stored as blanks. Most sections keep one shared `pts` list at the section level: `booked.airline.pts`, `booked.cruise.pts`, `booked.carRental.pts`, `booked.transfersPts`, `booked.toursPts`, `booked.themePark.pts`, `booked.train.pts`, `booked.bus.pts` — same as their shared Confirmation Number/Price/Notes. `booked.hotel` is the one exception: since it's already an array of independent per-stay entries (each with its own confirmation number, price, and notes), each entry gets its **own** `pts` list instead of one shared across every hotel on the trip — the add/remove-row UI and underlying `{program, amount, cost}` shape are identical, only the nesting differs. (Before this became a dynamic list, `booked.airline.pts` was a fixed set of up to 3 blocks; the array shape is unchanged, so old trips load without migration.)

A trip saved before `booked` existed has no such key at all — every reader treats it as `{}`/`[]`, so old trips open and re-save cleanly without migration.

**Summary** — the last subsection of Booked Trip Details (`tb-booked-summary`), a read-only rollup computed live off the form's current state rather than a static snapshot: every `pts` entry across all nine sections, totaled by `program`, plus every `price` field, every section's Insurance Premium, and every `pts` entry's `cost` summed into one **Total Cash Paid** figure (`computeBookedTripSummary()`/`bookedTripSummaryHtml()`). It recomputes on any `input`/`change` event anywhere in the modal (`refreshBookedTripSummary()`, delegated at the modal level since Price/Points Used rows are added and removed dynamically) — nothing here is persisted; it's purely derived for at-a-glance review while filling out the form.

The Summary also shows an **Invoice Number** line, but only when the trip has no Supplier linked — `refreshBookedTripSummary()` reads `!gv('tsup')` as a proxy for "invoiced to the client, not a supplier" (there's no dedicated field for this; a linked Supplier is treated as meaning that supplier holds the actual invoice, so surfacing "the" invoice number here would be misleading). Also recomputes on `tsup`'s own `change` event via the same delegated listener, so picking/clearing a Supplier immediately shows or hides the line.

### `db.vendors` (`V001`, ...) — "Suppliers" in the nav
`name`, `type` (Supplier / Referral Partner / DMC), `category` (Airline/Hotel/Cruise Line/Car Rental/Tour Operator/Other), `clientIds`, `website`, `notes`.

**`clientIds` is a purely manually-curated "Linked Clients" list**, edited via a checkbox list on the Add/Edit Supplier form (`openVendorForm()`) — it is *not* auto-derived from that vendor's trips. `getVendorStats(vendor)` already computes "which clients have booked with this supplier" live from `db.trips` (matching `supplierId`, or `airline`/`hotel` name for those two categories) every time it runs, so `clientIds` only needs to hold clients linked for some *other* reason (most commonly a Referral Partner with no bookings of its own to derive from). `saveTrip()` and the revenue importer (`finalizeImport()`) used to also push a client's id onto the linked supplier's `clientIds` as a side effect of linking a trip — this was redundant with `getVendorStats()`'s own live derivation and, since nothing ever removed the push (including deleting the trip), left stale client names stuck on a Supplier's card indefinitely; that auto-push was removed. The checklist itself used to only render when the vendor's Type was "Referral Partner" — now always visible for any vendor type, since `clientIds` was never actually restricted to that type in the data.

### `db.planner` (`PL001`, ...)
Follow-up tasks: `title`, `dueDate`, `done`, `clientId`, `clientIds`, `vendorId`, `tripId` (links back to the trip that spawned it), `email`, `completionNoteType`, `desc`, `createdAt`.

`clientId`/`clientIds` is the same primary/additional split `db.trips` uses for companions: `clientId` is the one client the Linked Client dropdown selects (drives the task's own `email` field autofill and is what a single-id lookup like `taskClientId()` returns), `clientIds` is every other client checked in the Additional Clients list. `taskClientIds()` returns the full deduped set (primary + additional), falling back to the linked trip's own `clientId`+`clientIds` only when the task has no client links of its own; `taskClients()` resolves that to the actual client records. Marking a task done (`logTaskCompletionNote()`) logs the completion note onto every one of those clients' records, not just the primary.

`email` autofills from every linked client's email, comma-joined (`linkedClientEmailsStr()`) — comma is the mailto: multi-recipient separator, so the "Email in Outlook" link reaches all of them at once with no extra work. It re-derives every time the Linked Client dropdown or an Additional Clients checkbox changes, and is still a plain editable text field if you need to override it by hand.

### `db.bookmarks` (`BM001`, ...)
Saved links to travel-related websites: `name`, `url`, `category` (one of `BOOKMARK_CATEGORIES` — Airline, Hotel, Cruise Line, Car Rental, Tour/Activity, Theme Park, Visa/Documentation, Currency/Weather, Tool, Other — the business type — optional), `audience` (one of `BOOKMARK_AUDIENCES` — Consumer, Travel Agent, or **Vendors** — which side of the business the link is for; a bookmark missing this field is treated as Consumer, so bookmarks saved before this field existed still display correctly), `notes`. `saveBookmark()` prepends `https://` onto whatever's typed if it doesn't already start with `http://`/`https://`, since a bare domain like `united.com` would otherwise be treated as a relative link and just reload the CRM itself instead of navigating out.

The Bookmarks page (`renderBookmarks()`) groups two levels deep: `bookmarkSectionHtml(audience, bookmarks)` renders one section per audience (**Travel Agent**, then **Consumer**, then **Vendors**), and within each, sub-groups by `category` — **Consumer/Travel Agent use `BOOKMARK_CATEGORIES`** order (Airline/Hotel/etc.), while **Vendors uses `BIZ_VENDOR_CATS`** instead (Printing/Web-Hosting/Accounting/etc. — the same category list the Vendors page itself uses, since a travel-industry category list wouldn't mean anything for a printer or web host bookmark); either way any category value not in that section's list — shouldn't normally happen — still gets its own group, just appended after the known ones. `bookmarkCategoryOptionsHtml(audience, selected)` builds the Add/Edit Bookmark modal's Category `<select>` the same audience-aware way, re-run on the modal's own Audience `<select>` `change` event so switching to Vendors swaps the category options live. `bookmarkTableHtml(items)` renders the actual per-category table, shared by every section.

Each category heading is collapsed by default and shows a live count (e.g. "AIRLINE (18)") — click it to expand. State is tracked in `window._bookmarkCategoriesCollapsed`, keyed by `audience+'|'+category` (so Travel Agent's Airline group and Consumer's Airline group toggle independently) — `!==false` means collapsed, so an explicit expand is what gets remembered, the same `window._tripGroupsCollapsed` pattern the Trips page uses.

`DEFAULT_BOOKMARKS` is a hardcoded starter pack (~114 entries) of consumer booking-site URLs and travel-advisor/agent-portal login URLs for the airlines/hotels/car-rental companies/cruise lines/tour vendors/theme parks in the app's existing constant lists — added on demand via the Bookmarks page's "+ Load Starter Bookmarks" button (`seedDefaultBookmarks()`), not seeded automatically. Each entry's `category` is the business type (e.g. `Airline`) regardless of whether it's a consumer or agent link — the agent-login entries additionally set `audience:'Travel Agent'` so they land in the right section rather than needing a separate category. It skips any entry whose `name`+`category`+`audience` already exists in `db.bookmarks`, so the button is safe to click repeatedly (e.g. after adding new vendors to the starter list in a future update). A handful of entries carry a `notes` value flagging them as unverified (e.g. "verify before relying on this link") where the underlying research could not fully confirm the exact portal URL; a few known vendors (Southwest/Frontier agent portals, Hyatt/Wyndham/Avis/Budget agent portals) were omitted entirely rather than guessed, since no distinct branded portal could be confirmed to exist for them.

**`category:'Award Tools'`, `audience:'Travel Agent'`** is award-booking-tool links — Seats.aero, ExpertFlyer, Point.me, AwardWallet. No consumer equivalent for any of them; they're advisor-only tools for searching award availability and tracking client mileage balances across programs. (This category was originally added as the generic `'Tool'`, already present in `BOOKMARK_CATEGORIES` from the start but with no entries until these four were added — renamed to `'Award Tools'` shortly after, since that's the only thing it actually ended up holding.)

## 3. Navigation / Features

The left nav has 14 `go()`-driven sections (`view` state: `dashboard`, `clients`, `trips`, `ccconsulting`, `referrals`, `vendors`, `bizvendors`, `planner`, `reports`, `calendar`, `email`, `marketing`, `analytics`, `bookmarks`) plus seven plain external links (Miles Man Site, WordPress Admin, Google Drive Folder, Mailchimp, Canva, Vercel, GitHub — see the Bookmarks section below).

### Dashboard
A **Quick Search** box, summary stats (client count, total trips, upcoming, **Total Revenue**, points deployed, **Blog Followers**, **Instagram Followers**, **X Followers**, **TikTok Followers**), a **Revenue by Section** card, a **Mailchimp** stats card, a **Most Recent Email** card, an **Upcoming & In Progress Trips** table, a top-clients-by-revenue list, and a Planner tasks card.

**Upcoming & In Progress Trips** (`#dash-view-all`'s card, formerly labeled "Recent trips" and sorted by most-recently-added `db.trips` record) now only ever shows trips whose `tripLifecycleCategory()` is `'inTrip'` or `'upcoming'` — Planning/Completed/Cancelled trips never appear here regardless of when they were added — and excludes non-travel income (`isNonTravelIncomeTrip(t)`, same as the Trips page itself, since a Referrals/Credit Card Consulting record has no travel dates and would never meaningfully belong in a trip-urgency list anyway). Sort order is category first (every in-progress trip before every upcoming one), then `departDate` ascending within each group, so the very next thing happening — whether that's a trip already underway or the soonest one still to come — is always at the top. Capped to the first 6 after sorting/filtering; **View all** still goes to the unfiltered Trips page.

**Blog Followers** is fetched independently of the rest of the Dashboard's stats — it reads `mm_wp_token` from localStorage and, if present, calls the same `/sites/$site/stats` endpoint (via the `wordpress-stats.js` proxy) `loadWordpressStats()` uses on the Analytics tab, but populates just this one `#dash-followers-val` number rather than reusing that function (which targets a different container). Shows `—` until that fetch resolves (or forever, if WordPress isn't connected). Clicking the tile navigates to the Analytics tab with the Blog Followers drill-down section pre-expanded and scrolled into view — the same `window._analyticsCollapsed['wp-followers']=false` + scroll pattern the Analytics page's own Blog Followers stat tile uses (§4.7).

**Instagram Followers** follows the identical independent-fetch pattern — reads `mm_fb_token`, and if present calls `fetchInstagramAccountId()` (§4.8) then `GET /{ig-id}?fields=followers_count`, populating `#dash-ig-followers-val`. Clicking it navigates to the Analytics tab and scrolls to the Instagram section of the Facebook card (`#ig-analytics-body`) — no collapse-state toggle needed, since unlike Blog Followers' drill-down section, Instagram's stats aren't behind a collapsible section.

**X Followers** is the one follower tile that does *not* fetch on render: X bills per API read (§4.10), so it goes through `xFollowerSnapshot(false)`, which serves a `localStorage`-cached snapshot and only actually calls X on the first load of a new calendar day. The Analytics tab's X card shares that exact same cache, so having both open across a day still costs one read total. Below the number it shows a follower delta (`xDeltaHtml()`) computed from two cached snapshots — free, and the only reason a day-over-day figure exists at all, since X has no account-level "yesterday" endpoint. Clicking navigates to the Analytics tab's X card.

**TikTok Followers** is back to the fetch-on-render pattern (TikTok's Display API has no per-request cost, §4.11, so there's no reason to cache it the way X's tile has to) — reads `mm_tiktok_token`, and if present calls `tiktokApi('/v2/user/info/', {query:{fields:'follower_count'}})`, populating `#dash-tiktok-followers-val`. Clicking navigates to the Analytics tab's TikTok card.

**Quick Search** (`dashQuickSearchRowHtml()`, wired inside `renderDash()`) is a single text input searching `db.clients` (name or email), `db.vendors` (Suppliers, name only), and `db.bizVendors` (Vendors, name only) all at once, live as you type — no submit button. Results render as a flat list capped at 15, each tagged with a color-coded type badge matching the Planner Type column's convention (`b-blue` Client, `b-green` Supplier, `b-amber` Vendor) plus a subtitle (email for clients, category for Suppliers/Vendors); clicking a row opens that record directly (`openClientForm`/`openVendorForm`/`openBizVendorForm`). Trips aren't included — this is for jumping to a *record*, and the existing Trips-page search already covers trip lookups.

**Revenue by Section** breaks the headline Total Revenue figure down into the three pages that hold trip-record revenue — Trips, Credit Card Consulting, Referrals and Promo — each a `totalValue` sum filtered by that page's own matcher (`!isNonTravelIncomeTrip(t)`, `isCreditCardConsultingTrip(t)`, `isReferralIncomeTrip(t)` respectively, see the Trips section below), so the three tiles always add up to Total Revenue. Clicking a tile navigates to that page.

**Mailchimp** (`#dash-mc-stats-body`) shows the identical six-tile grid as the Analytics tab's own Mailchimp card — Subscribers, Subscribers Added Yesterday, Unsubscribed Yesterday, Campaigns Sent, Open Rate, Click Rate — via the same shared `loadMailchimpStatsTiles()` (§4.3), so the two are always in agreement. The Campaigns Sent tile can't expand the Recent Campaigns section in place the way it does on the Analytics page itself, so here it navigates to the Analytics tab first (`onCampaignsClick` override), then expands and scrolls to it. **View all** just navigates to the Analytics tab.

**Most Recent Email** (`#dash-mc-latest-body`) shows the same one-line summary of the most-recently-sent Mailchimp campaign as the Analytics tab's own collapsed Recent Campaigns section (§4.3) — both call the shared `loadLatestMailchimpCampaignSummary()`, so the two never disagree. Reads `—`/a connect prompt until a Mailchimp audience has been chosen; clicking the line itself opens the same per-recipient activity modal a campaign row on the Analytics tab would. **View all** jumps to the Analytics tab with the Recent Campaigns section expanded and scrolled into view, same pattern as the Blog Followers tile above.

**Total trips matches the Trips page's own count**, not a raw `db.trips.length`. It's `countTripSummaryLines()` (the same grouping-aware counter the Trips page's own "Trips" stat uses, see below) run against `db.trips` filtered the same way the Trips page filters by default — non-travel income excluded (`!isNonTravelIncomeTrip(t)`) and Cancelled excluded (matching the Trips page's default status filter, `STATUSES` minus Cancelled) — so a linked-trip group counts once here too, and the number on Dashboard never disagrees with what you'd see landing fresh on the Trips page. This is independent of whatever status filter the Trips page was last left on, since Dashboard always computes against this fixed "default view" population rather than reading `fStatus`. The stat's drill-down list uses this same filtered/grouped population (still one row per trip record, not per group, like every other stat drill-down).

**Upcoming counts collapsed summary lines on the Trips page**, not raw trip records with a future `departDate`. `tripGroupsByCategory(dashTrips, 'upcoming')` — a sibling of `countTripSummaryLines()` — groups `dashTrips` the same way (`tripLinkGroups()`, deduped by `tripGroupKey()`) and keeps only the groups whose *representative* (earliest-departing member, the same one `tripSummaryLineHtml()` and the Trips page's group-aware Status sort key off — see the Trips section's sort note below) falls into the `'upcoming'` lifecycle category; `.length` is the stat, and flattening every matched group's members is the drill-down list. Before this, the stat just counted individual records with `departDate>=today()`, which could disagree with the Trips page in two ways: a multi-leg linked group counted once per member instead of once per summary line, and a trip whose color/category came from date-derived logic (rather than `departDate` alone) wasn't necessarily counted the same way the page's own yellow highlighting would.

**Points deployed** (`tripBookedPoints()`) totals only the granular redemption entries recorded in each trip's Booked Trip Details — every section's `pts[].amount` (Airline, Cruise, Car Rental, Tours via `toursPts`, Theme Park, Train, Bus, plus every hotel entry's own `pts[].amount`) — not the simple top-level `pointsUsed` field on the trip's basic form, which is a separate, less precise number that isn't rolled into this total. A hotel entry saved before its points became a `pts` list falls back to its old single `amount` field so old trips aren't undercounted. The drill-down list is built the same way, one row per trip with `tripBookedPoints(t) > 0`.

The **Upcoming** stat tile's drill-down list is exactly `[].concat.apply([], upcomingGroups)` — the same `tripGroupsByCategory(dashTrips, 'upcoming')` result the tile's own count (`upcomingGroups.length`) comes from, so the two can never disagree. **Total Revenue**'s drill-down is every trip in `db.trips` (`db.trips.map(tripRow)`), matching `s.value`'s own unconditional `db.trips.reduce()` exactly — a prior version filtered this list to Completed/Upcoming trips only, which silently hid any Planning/In Progress/Cancelled trip's revenue from the very list meant to explain the headline number it was still counted in; that filter was removed so the drill-down always adds up to precisely what's shown, same invariant every other clickable stat on this page follows. The other stat tiles' drill-downs (Clients, Total trips, Points deployed) are unfiltered by status too.

**Planner tasks — today & overdue** card: the same "Today & Overdue" definition Planner's own date filter uses (`!t.done && t.dueDate && t.dueDate<=today()`), sorted most-overdue-first, capped to the top 10 so a backlog doesn't blow out the card. Each row shows the task title, every linked client (if any, each independently clickable to open that client), and due date (styled red if overdue); clicking anywhere else on the row opens that task in `openTaskForm()`. **View all** navigates to the Planner page and forces its date filter to "Today & Overdue" (`window._plannerDateFilter='today-overdue'`) so what you land on matches what the dashboard card just showed, regardless of whatever filter Planner was last left on.

### Clients
Searchable/sortable table (search matches name, email, city). Click a row to open the Add/Edit Client modal with the full field set from §2, plus a note-taking timeline (`notesLog`) with typed entries (Email Sent/Received, Initial Call, Follow-up, Post-Trip Follow-up, General, Trip Import, Text Message Sent/Received, Lead, Mailchimp Email Sent, Facebook Message — `NOTE_TYPES`), file attachments, and inline Paying Client / Subscriber toggles.

**Sync Subscribers** button in the toolbar (`reconcileSubscribers()`, §4.3c) pulls the current Mailchimp and Jetpack subscriber lists and opens a review modal for anyone whose CRM Sub checkbox doesn't match — see §4.3c for the full flow. The button carries a red count badge whenever `db.jetpackRemovalQueue` (§4.3a) is non-empty, since that queue also needs attention.

The client form also lists that client's own `db.planner` tasks (`taskClientIds(t).indexOf(id)!==-1`, sorted open-before-done then by due date) — this matches whether the client is the task's primary Linked Client or one of its Additional Clients, so a task tied to more than one client shows up on every one of their records, not just the primary's. **+ Add Task** creates one already linked to this client. Clicking a `.client-task-row` opens the real task editor (`openTaskForm(taskId)`), same as everywhere else tasks are opened (Dashboard, Planner) — it used to open a stripped-down `openTaskNotes()` modal instead (a "log a note against this task's linked records" form with no due date field), which is why the due date wasn't reachable from here before.

**Each trip row in the client's own Trips list has a delete button** (`.del-client-trip`, reusing `delTrip()`'s confirm/snapshot/save flow) so a bad or duplicate trip record spotted while reviewing a client's booking history can be removed right there, without leaving the modal to find it on the separate Trips page. Deleting reopens the same client form afterward (`openClientForm(id)` again) rather than just calling `render()`, since `render()` only refreshes `#main` and would otherwise leave the modal still showing the trip that was just deleted.

**Email is no longer required to save a client** — `saveClient()` used to refuse to save at all (silent no-op past a toast) unless both Full Name and Email were filled in. That blocked editing any client created with a blank email, which happens routinely via the revenue importer's auto-create path (§3 Suppliers) whenever a report row carries no email data — e.g. a referral-bonus line item for someone who's only in the system via that one transaction. Name is now the only requirement.

Stats: Clients, Total Revenue, Total Trips.

### Trips
Searchable/sortable table with inline status badges, points/value columns, supplier links, and invoice numbers. Stats: Trips, Total Revenue.

**Every trip renders as a collapsible summary line, collapsed by default.** `tripLinkGroups()` computes connected components over `linkedTripIds` across *all* `db.trips` (not just the current filtered/sorted list, so a group's membership doesn't shift depending on what search/status filter happens to be active) — a linked-trip group has 2+ members, an unlinked trip is its own 1-member "group". `tripTableBodyHtml()` walks the filtered/sorted list in its existing order and, the first time it reaches a member of a group, renders `tripSummaryLineHtml()`: for a 2+-trip group, a full-width row with a link icon, client name(s), every distinct non-blank `booked.tripName` found across the group's legs (joined with `/` if they differ — usually there's just one, since a multi-city vacation's legs typically share one name), every member's destination joined in chronological order, the date range spanning all of them, a trip count, and — added onto the end via `tripSummaryLineInfo()`'s new `totalRevenue` field (`sorted.reduce(...t.totalValue...)`, the same field the Clients page's own Total Revenue column sums) — the combined `totalValue` across every member, shown as `$X,XXX` and omitted entirely when it's zero (e.g. a trip with no revenue on file yet); for a lone trip, the same layout minus the trip name/icon/count, but the revenue figure still shows since it's not group-specific. If expanded, the group's members follow as full detail rows (`tripRowHtml(t, isGroup)` — a 2+-trip group's rows get an indented `&#8618;` on the Client cell, a lone trip's doesn't), then the loop skips those members later on. This sits on top of the existing sort/filter/search, not instead of it: a group's position in the table follows wherever its first-encountered member lands under the active sort, and its own row ordering is always chronological by depart date regardless of the active sort column. `tripSummaryLineHtml()` is shared with the Dashboard's own upcoming-trips list (`dashTripSummaryLinesHtml()`), so the revenue figure shows there too, for free.

**Default sort is "upcoming first"**, not the prior newest-added-first: `window._tripSortCol` defaults to the special value `'upcoming'` (still overridden by clicking any column header, same as before). Its comparator ranks every trip — soonest-upcoming/currently-in-progress trips first (`departDate>=today()`, ascending so the very next trip is at the top), then past trips (`departDate<today()`, but *descending* so the most recent past trip sits closest to the "now" boundary rather than the oldest trip in history), then no-date trips last; a group's rank is driven by its earliest-departing member, matching how its own date-range display is computed.

**Each summary line is color-coded by `tripLifecycleCategory()`** (again keyed off the earliest-departing member for a group) — status overrides date, since Cancelled/Planning/Upcoming/**In Progress** are explicit choices: **red** Cancelled, **blue** Planning, **yellow** Upcoming regardless of what `departDate` actually says (e.g. a stale/incorrect past date on a trip explicitly marked Upcoming still shows yellow, not orange), **green** In Progress regardless of dates (same override precedence — a trip explicitly marked In Progress reads as currently-traveling even if its dates say otherwise), and only for anything else (Confirmed/Completed/blank) does it fall to a date-derived category — **green** if today falls within `[departDate, returnDate]` (this is the *derived* path to the same green the explicit `In Progress` status produces), **yellow** if `departDate` is still ahead (the derived path to `Upcoming`'s yellow), **orange** otherwise (past, or dateless-and-not-Planning — a trip with only a `departDate` and no `returnDate` falls back to treating `departDate` itself as the end date, so it reads as in-progress only on that single day and orange/past afterward; it used to have no upper bound at all when `returnDate` was blank, making a years-old dateless trip register as "in progress" forever). `TRIP_LIFECYCLE_COLORS` holds the bg/text pair per category, and `CATEGORY_LABELS` the matching human-readable text (Upcoming/In Progress/Completed/Cancelled/Planning) shown right in the summary line itself (`· <status> ·`, between the client/destination label and the date range) — keyed off the same category the color comes from, not the trip's raw `status` field, so the text can never disagree with the color it sits next to even when the category is date-derived rather than explicit. `STATUSES` (§2) is `['Planning','Confirmed','Upcoming','In Progress','Completed','Cancelled']` — referenced dynamically everywhere a status list is needed (the trip form's own Status dropdown, the multi-select status filter, the AI Report/Assistant tool schemas), so adding a status here never requires hunting down a duplicated hardcoded list elsewhere.

**Trip status auto-transitions by date**, independent of the color-coding above — `autoUpdateTripStatusesByDate()`, on the same 5-minute timer as the other automatic background checks (§4.4/§4.5/§4.6), actually *writes* `t.status` rather than just deriving a display category from it: a trip whose `[departDate, returnDate]` range (or just `departDate` alone, for a dateless-return trip) contains today becomes `'In Progress'`, and once that range has passed it becomes `'Completed'`. Planning and Cancelled are deliberate holds and are never touched, matching `tripLifecycleCategory()`'s own "explicit status wins" precedence; every other status (Confirmed, Upcoming, In Progress, Completed) is eligible, moving forward only when its computed status actually differs from the stored one (idempotent — no snapshot()/save churn on a no-op tick, and no undo-stack entry either, same reasoning `checkForUpcomingBirthdays()` uses for its own automatic writes).

**Clicking the Status column header sorts by that same color/category** rather than alphabetically: `LIFECYCLE_SORT_RANK` fixes the order inTrip(0) → upcoming(1) → planning(2) → past(3) → cancelled(4), an early-return branch in the same sort comparator that handles `tripSortCol==='upcoming'` (both bypass the generic `av`/`bv` string/number comparison below them, since neither reduces to a single sortable field). `tripSortDir` still flips it (desc reverses the whole rank order, not just ties) — within a tied category it falls back to `departDate` ascending as a stable secondary sort. The column header's `title` tooltip spells out the order for anyone who hasn't read this.

**The Status sort is group-aware**, via a `repCategory(t)` helper computed once per render (`tripLinkGroups()` + a per-member cache, `repCategoryCache`) rather than calling `tripLifecycleCategory(t)` directly on each record being compared. This matters because a linked-trip group's summary line displays its color/label from only its *earliest-departing* member (`tripSummaryLineHtml`'s own `sorted[0]`) — sorting by each individual record's own category instead (the original implementation) could rank a group's row using a *different* member's status than the one actually shown, so the row would land somewhere that visually contradicted its own color (e.g. a group showing orange/Completed appearing among the yellow/Upcoming rows). `repCategory()` resolves every member of a group to that same earliest-departing member's category before ranking, so a group's sort position always agrees with what it displays — exactly the bug report ("the sort is not correct") this fixes.

**Non-travel income never shows on this page.** `renderTrips()`'s filter drops any trip where `isNonTravelIncomeTrip(t)` is true — the union of two case-insensitive substring matchers against `t.product` (the revenue importer's Item/Class text, §2; only checks `product`, never `notes` or any client-referral field, so it can't misfire on an unrelated "client was referred by..." note): `isCreditCardConsultingTrip()` for `credit card consulting`, `non-cash bonus`/`noncash bonus`, and `isReferralIncomeTrip()` for bare `referral` (not `referral fee`, so it also catches whatever QuickBooks' actual wording turns out to be, e.g. "Referral Commission") or `promo`. A record can only ever land on one page: `isCreditCardConsultingTrip()` returns `false` outright whenever `isReferralIncomeTrip()` matches, so a record straddling both patterns (e.g. "Non-Cash Bonus:Referral Program") is treated as a referral, not a CC-consulting record. These are still plain trip records under the hood (same `db.trips` array, same Add/Edit Trip modal, same `delTrip()`) — they're just filtered out of this specific view and shown on their own page instead, see **Credit Card Consulting** and **Referrals and Promo** below.

### Credit Card Consulting
A second, differently-filtered view onto `db.trips` — not a separate entity type. `renderCreditCardConsulting()` and `renderReferrals()` (see below) both call one shared `renderNonTravelIncomePage(cfg)`, passing a `matchFn`/title/empty-message/search-state-key; since only one view is ever mounted into `#main` at a time, both pages safely reuse the same `#cc-search`/`.cc-row`/etc. ids, with `cfg.searchKey` (`_ccSearch` vs `_referralSearch`) keeping each page's search box independent so switching pages doesn't carry over the other's search text. This page shows exactly the trips `isCreditCardConsultingTrip(t)` matches (see above): a plain sortable-by-date table (Client, Item, Date — `departDate` falling back to `invoiceDate`, Points, Value, Notes, edit/delete), a text search filtering by client name/Item/notes, and stats for record count and total value. **+ Add Record** opens the same `openTripForm()` modal used everywhere else — there's no dedicated creation flow, so a manually-added record only lands on this page (and off the Trips page) once its **Product** field contains one of the matched phrases; nothing else about the form is different. No linking/grouping/collapsing (unlike Trips) — these aren't real bookings with itineraries to group.

### Referrals and Promo
Same `renderNonTravelIncomePage(cfg)` shell as Credit Card Consulting above, filtered on `isReferralIncomeTrip(t)` instead. A record only shows here (never also on Credit Card Consulting) even if its `product` text happens to also contain a CC-consulting phrase — see the precedence rule above.
**Clicking a summary line collapses/expands it** (a ▾/▸ chevron reflects the state). State is tracked in `window._tripGroupsCollapsed`, keyed by `tripGroupKey()` — a stable signature (member trip IDs, sorted and joined) rather than array position, so it survives re-renders from sorting/filtering/searching the same way `window._tripSortCol` does. Collapsed is the default (`collapsedGroups[key] !== false` — absence of an entry means collapsed, same as a group nobody's touched yet), so an explicit *expand* is what gets remembered, not the other way round. A collapsed group's detail rows are simply not rendered (`tripTableBodyHtml()` skips the render loop but still marks every member as `rendered` so they don't fall through to a second, unwanted render) — the summary line itself, and its own membership computation, are unaffected by collapse state.

**The "Trips" stat counts summary lines** (`countTripSummaryLines()` — one per linked-trip group plus one per standalone trip), not raw trip records. The count doesn't change based on collapsed/expanded state, since collapsing changes how much of a group is visible, not how many groups exist.

**`countDistinctTrips(clientId)`** (used for the Clients page's own per-client trip count, its sort-by-Trips column, the Dashboard/list Total Trips stats, and CSV export) now folds in the same Linked Trips grouping `countTripSummaryLines()` uses, on top of its own pre-existing invoice-number dedup — two of a client's own trip records collapse into one count whenever either applies: they share an invoice number, or they're in the same `tripLinkGroups()` cluster. It used to only apply the invoice-number rule, so a client with a manually-linked multi-city vacation (e.g. a NYC leg + a Paris leg) showed 2 trips there while the Trips page itself showed the same vacation as a single collapsed row — the two counts now agree. The invoice-number check itself also had a real bug fixed at the same time: it only ever read `t.invoiceNum`, a field the revenue importer sets but the manual trip form's own "Invoice Number" field never does (that one writes `t.bookingRef`) — meaning invoice-based deduping silently never worked at all for any trip that wasn't revenue-imported. It now checks `t.invoiceNum||t.bookingRef`, the same fallback the Invoices report (§3) and the `invoiceNum` field's own docs (§2) already use elsewhere. Implemented as a union-find over just that client's own trips (rather than reusing `tripGroupKey()`/`countTripSummaryLines()` directly, since those only know about `tripLinkGroups()` membership, not invoice-number sharing) — a trip with neither an invoice number nor any Linked Trips membership still counts on its own, unchanged from before.

**Status filter is multi-select**, defaulting to every status except Cancelled (`fStatus` is now an array, not a single string — `STATUSES.filter(s => s!=='Cancelled')` both on initial load and whenever `go()` navigates back to the page). The dropdown is a custom checkbox panel (`#trip-status-filter-btn`/`#trip-status-filter-panel`, toggled the same simple way the sidebar's `.menu-toggle-btn` groups are — no outside-click auto-close) rather than a native `<select multiple>`, so the button's own label always summarizes the current selection ("All statuses", "All except Cancelled", "No statuses", a single status name, or "N statuses"). Unchecking every status is a valid state — it just filters the table down to nothing, same as any other filter combination that matches zero trips.

The Add/Edit Trip modal covers flight, hotel, cruise, and generic per-brand loyalty-balance sections (shown/hidden based on which client is selected, mirroring their stored balances), plus a **Booked Trip Details** section — see §2's `booked` field for the full schema. It's organized into Airline / Hotel / Cruise / Car Rental / Tours / Theme Park / Train / Bus, each with its own confirmation number field and its own "Points Used" block — a dynamic, add-any-number-of-rows list of miles/points redemptions (program + amount + cash cost), with the program dropdown combining every airline, hotel, and credit card option (§2's `pts`). Every section keeps one shared Points Used list except Hotel, which gives each individual hotel entry its own list (since Hotel is already a per-stay list with its own confirmation number/price/notes per entry). Cruise Line selection cascades the Ship Name and Cabin Type dropdowns, reusing the same option lists as the quote builder (`getQuoteConfig`).

### Groups (`db.groups`, `'GRP'` ids)
A Group links whole collapsed-trip-line units (a standalone trip, or an already-linked-legs vacation cluster — exactly what the Trips page itself shows as one summary line) together under one named, notable umbrella — e.g. a big multi-family reunion booked as several separate, unrelated trip records that still belong together in spirit. This is a *different* relationship from a trip's own `linkedTripIds` (which links individual legs of one vacation into one Trips-page summary line, §3 above) — a Group links whole summary-line units to each other, one layer up. `db.groups[i] = {id, name, tripIds, notesLog}` — `tripIds` is a flat list of member trip ids; which of those form their own `tripLinkGroups()` sub-clusters is re-derived live at render/pick time rather than stored, so a Group never goes stale if a member trip's own `linkedTripIds` change later.

**The Groups page renders each group as its own collapsible summary line** (`groupSummaryLineHtml()`, `window._groupsCollapsed` tracks collapsed state the same key'd-by-id way the Trips page's `window._tripGroupsCollapsed` does) — folder icon, group name, a status label/color and date range derived from the *earliest-departing* member trip across the whole group (not just within one sub-cluster — a group spanning a currently-in-progress trip and a further-out upcoming one still reads green, the same convention an individual multi-leg trip's own color already follows), a trip count, and the combined `totalValue` across every member trip (shown as `$X,XXX`, omitted when zero) — the same total the Trips page's own collapsed line sums (§3 above). Expanding a group renders its member trips via `tripTableBodyHtml()` — the exact same function/markup the Trips page uses, so a group's expanded body still further collapses/expands its own multi-leg sub-clusters independently, and clicking a trip row still opens `openTripForm()`.

**Groups sort the same way the Trips page's own default (Status) sort does** — `sortedGroupsByStatus()` ranks each group by its representative member's category (in progress, then upcoming, then planning, then completed, then cancelled — `GROUP_LIFECYCLE_SORT_RANK`, the same priority `renderTrips()`'s Status column uses), ties broken by nearest date to today (dateless last), falling back to alphabetical-by-name only when neither group being compared has a member with a date at all. This replaced a plain alphabetical-by-name sort — a currently-actionable group (something happening now or coming up soon) surfaces near the top of the page instead of wherever its name happens to fall in the alphabet. Unlike the Trips page, this is a fixed default with no clickable column headers to change it — a group's own summary line doesn't expose the same per-trip columns (Client, Destination, etc.) a raw trip row does, so there's no equivalent set of columns to sort by.

**Add/Edit Group** (`openGroupForm()`) has a required **Group Name** field (editable at any time — re-opening an existing group via its ✏️ icon pre-fills the current name, and Save Group persists a changed name the same as any other field) and a **Trips** checklist (`allTripSummaryUnits()` — one row per collapsed-trip-line unit across all of `db.trips`, filterable via a live search box) for picking which units belong to the group; a unit already linked to this specific group stays visible in the picker even if it would otherwise be excluded (e.g. a non-travel-income record like Credit Card Consulting/Referrals — §2/§3's `isNonTravelIncomeTrip()`), so re-opening a group to edit it never silently drops an existing member. A note added on the group form cascades onto every client linked to any member trip and gets appended to each member trip's own `notes` field (`cascadeGroupNoteToClientsAndTrips()`) — trips have no `notesLog` array of their own, so this appends a timestamped line rather than pushing a structured entry.

### Suppliers (`vendors`)
Vendor/partner directory with per-vendor stats (trip count, linked clients, revenue) computed live from `db.trips`. Page-level stats: Total Suppliers, Total Trips, Total Clients, Total Revenue.

**Website** (`v.website`) has existed on the Add/Edit Supplier form since the beginning but was never actually shown on the Supplier card — it was write-only. The card now renders it as a clickable `target="_blank"` link (same `https://`-prefix-if-missing + 🌐 icon treatment `renderBizVendors()` already used for Vendors, see below), right under the contact name/email/phone line.

**Revenue import assigns status directly from the travel date, never `'Completed'` or `'Confirmed'` unconditionally.** `extractRevenueRow()` sets `status` to `'Upcoming'` if the row's derived travel date is in the future, `'In Progress'` if it's today, or `'Completed'` if it's already past — the same three-way split `autoUpdateTripStatusesByDate()` (§3 Trips) uses to keep any trip's status current going forward. An intermediate `'Confirmed'` status previously stood in for "paid but not yet completed" on future-dated imports (before that, everything imported was hardcoded `'Completed'` regardless of date); both were superseded once the real date-derived statuses could be computed directly at import time, since they're strictly more precise. A one-time migration in `loadDB()` corrects any already-imported trip (identified by `invoiceNum`) still sitting at `'Completed'` or `'Confirmed'` to its correct status under this scheme; a trip without `invoiceNum` (manually entered, including one a person deliberately set to `'Confirmed'` by hand — still a selectable status on the trip form) is left untouched.

**Revenue import creates a missing Supplier automatically.** `extractRevenueRow()` still matches a row's Name against existing Suppliers by exact case-insensitive name first, but if nothing matches and Name differs from Class (i.e. Name is presumed to be the supplier being paid), it now carries that candidate name forward instead of leaving the trip supplier-less. `finalizeImport()` creates the Supplier record for it — before creating/linking the client or trip for that row — deduping by name within the same import batch so multiple rows naming the same new supplier don't create duplicates. This applies to both the manual "Clean & Import Revenue File"/"Import Revenue CSV" paths and the automatic Outlook revenue-report email sync (§4.4), since they share this same pipeline. Re-running an import after a supplier now exists (auto-created or manually added) also backfills it onto any already-imported trip that was missing one, the same way it already backfills `invoiceDate`. The weaker Item/Class-text substring match (used only when Name itself doesn't clearly indicate a supplier) still never auto-creates — that heuristic is too speculative to safely mint new Supplier records from.

**Client-name matching is tolerant of report truncation.** QuickBooks' "Sales by Customer Detail" PDF export truncates the Class column to its fixed print width, appending literal `...` when a name doesn't fit — e.g. `"Bakhash"` becomes `"Bak..."`, or a long first name can swallow the whole last name down to nothing but `"..."`. The importer's client matching used to require an exact first+last match, so any truncated row simply never matched a real client no matter how unambiguous the visible prefix was — a real report showed this concretely: an existing client whose Class value truncated to `"Adam Ga..."` never matched their actual record (`"Garth, Adam"`), and one truncated to `"Heidi Bak..."` fell through matching entirely and got auto-created as a second, duplicate client instead of resolving to the existing `"Bakhash, Heidi"`. `matchClientByName(name)` — shared by both `startRevenueImport()`'s pre-pass and `finalizeImport()`'s per-row match, which used to be two separately-maintained implementations of the same logic — now treats a `"..."`-truncated segment as a known *prefix* rather than requiring the full segment to match (`"Bak..."` matches a stored last name of `"Bakhash"`), only resolving when exactly one client fits so an empty/ambiguous prefix never guesses wrong.

For a genuinely new client (no existing record to match), `cleanNewClientName(name)` builds the name actually stored on creation — used by both the unattended auto-create path (`autoResolveUnmatched`, used by the automatic revenue-report email sync since nobody's necessarily present to click through the Unmatched Client modal) and the modal's own "+ Add as new client" button. It never bakes a literal `"..."` into the stored name (an earlier version did, producing real client records like `"..., Jonathan"` that sorted to the top of the Clients list and were easy to miss entirely, making a successful-but-garbled auto-create look identical to the row having been silently dropped) — but it also never silently drops the fact that a segment is incomplete, either: a *partially* truncated segment keeps a trailing "…" marker (`"Skyler Lip..."` becomes `"Lip…, Skyler"`, not the plausible-looking-but-wrong `"Lip, Skyler"`), while a segment truncated down to zero known characters is omitted rather than reduced to a bare "…" (`"Jonathan ..."` becomes just `"Jonathan"`, findable under "J" instead of an ellipsis). The unmatched-client modal also flags a truncated-looking name directly in its own text ("name is cut off in the source report") so a real, unambiguous match doesn't get clicked "Skip" out of confusion about what the garbled name even is. The import's closing "Imported N trips" toast reports a count of any incomplete-name clients created in the batch, so this doesn't require digging through the Debug Panel to notice.

**Contacts** — a vendor can hold any number of people (`vendor.contacts`, each `{id, name, title, email, phone, propertyName, notesLog}`, id prefix `VC`, globally unique across every vendor's contacts array via `newId('VC', allVendorContacts().map(x=>x.contact))` rather than scoped to one vendor — needed so a task's `vendorContactId` and the Outlook sync can resolve a contact without also knowing which vendor it belongs to; `allVendorContacts()`/`findVendorContact(id)` are the two lookup helpers). The Supplier form's own "Contacts" section (between Notes and Clients with Bookings) lists each as a Name/Title/Email/Phone summary row — clicking one, or **+ Add Contact**, opens a dedicated `openVendorContactForm(vendorId, contactId)` modal that mirrors the client form's own notes-timeline + task-list pattern almost exactly: the same `#notes-log`/`.note-entry`/`.note-ts-link` markup and the same generic `addNoteEntry()`/`openNoteExpand()` helpers (unmodified, since those never hardcoded anything client-specific), a Tasks list scoped to `db.planner` tasks where `vendorContactId` matches, and a **+ Add Task** that saves the contact first if it's brand new (same "must save first" reasoning as the client form's own +Add Task) then opens a fresh task pre-linked to it. A trash icon on each contact row in the Supplier form deletes it directly (with confirm), without opening the contact modal. `saveVendor()` never touches `contacts` itself (it's not part of that form's own field set), so editing the rest of a Supplier's fields can't accidentally drop its contacts.

**Contact Emails** — a read-only section on the Supplier form (right after Contacts) that merges every contact's own `Email Sent`/`Email Received` notes into one newest-first feed, so seeing a supplier's full email history no longer means opening each contact individually. Built by flattening `(d.contacts||[]).map(c=>c.notesLog||[])`, filtering to just the two email note types, and sorting by `ts` descending — every other note type on a contact (General, Follow-up, etc.) is left out, since this is specifically an email history, not a general activity feed. Each entry shows its timestamp, a Sent/Received badge, which contact it came from, and the note text, and reuses the same `.vendor-contact-link` click class the Contacts list above uses — clicking one opens that contact's own `openVendorContactForm()`, where the note actually lives and can be edited/retyped/deleted; there's no edit affordance in the merged view itself, since a note only knows which contact it belongs to via this section's own lookup, not anything stored on the note.

**Properties** (`vendorPropertiesListHtml()`/`readVendorProperties()`, shown only when a Supplier's Category is Hotel) is a single scrollable multi-select `<select>` of property names rather than one form row per property, since a major brand can carry hundreds of them (Hyatt alone ships with 326 in `HOTEL_PROPERTY_SEEDS`, §2) — a row-per-property layout was unusable at that scale. **+ Add**/**Remove Selected** manage the plain name list; a property's id is never tracked through add/remove, just re-numbered sequentially (`'HP'+(i+1)`) on every save, since nothing keys off it by id — the Booked Trip Details Property picklist (`hotelPropertyOptionsHtml()`) matches by name.

**Property Email** — a small field below the Properties list/Add/Remove row, active only when *exactly one* property is selected in the listbox above it (a note only ever belongs to one property, so a multi-selection or an empty selection disables it, with a hint line explaining why). Reads and writes straight to/from that specific `<option>` element's own `data-email` attribute — there's no separate `{name, email}` array kept in sync in memory at this point, just the `<select>` itself — and appends a trailing ✉ to a property's label the moment an email is saved on it, so a property with one on file is visible at a glance while scrolling a list of hundreds. **Save Email** only updates the DOM; like every other field on this form, it isn't actually persisted until **Save Supplier** is clicked, at which point `readVendorProperties()` carries each option's current `data-email` (and re-numbered id) into the saved `property.email` field.

**A Contact can be tied to one Property** — the Add/Edit Contact form (`openVendorContactForm()`) shows a searchable **Property** field, populated by `hotelPropertyOptionsHtml(vendor.name, d.propertyName)` — the exact same function/data the Booked Trip Details Property picklist uses (`vendor.name` doubles as the "hotel brand" that function expects), only rendered when the Supplier's Category is Hotel and it actually has properties on file. Stored as `contact.propertyName`, matched by name rather than the Properties list's own re-numbered id, same convention `property.email` and the trip-side picklist both already use. `contactEmailPhoneLine(c)` — the shared summary-line renderer used by every contact list in the app (Supplier cards, the Supplier form's Contacts section, and the equivalent Vendor/biz-vendor views) — appends the property name onto that line whenever it's set, so a contact tied to a specific hotel (e.g. its own group sales desk) reads that way everywhere its summary line appears, with zero extra wiring needed for the Vendor/biz-vendor side, where `propertyName` simply never gets set.

**Property Contacts** — the reverse direction of the link above, surfaced from the Properties list itself rather than requiring a detour through the Contacts section. Mirrors the Property Email field's own selection rule: enabled only when *exactly one* property is selected in the listbox, reading straight off `d.contacts` (this form's already-loaded vendor data, no fresh lookup) rather than a separate array. `refreshPropertyContactsField()` filters `vendor.contacts` down to whichever ones have `propertyName` matching the selected property's bare name and lists them (name + title, `.property-contact-link` opening that contact's own `openVendorContactForm()`), or shows a "No contacts linked to `<property>` yet." hint when none match. A **+ Add Contact for This Property** button opens a brand-new contact form with the Property field already pre-selected — threaded through as a 4th `defaultPropertyName` parameter on `openVendorContactForm()`, used only when the contact being edited doesn't already have its own `propertyName` set (an existing contact's own saved property always wins). Saves a new/unsaved Supplier first if needed, the same "must save first" pattern the Contacts section's own **+ Add Contact** button already uses.

**Reclassifying a standalone Supplier as one property of another** (`moveSupplierIntoParent(childId, parentId)`) — for when a record, usually one auto-created by a revenue import from a single hotel's invoice (§ "Revenue imports create a missing Supplier"), turns out to be one property of a parent brand/group already in the CRM. The edit form's **"Actually a property of another supplier?"** section (only rendered when editing an existing record) offers a searchable `#vendor-merge-target` picklist of every *other* vendor; **Move as Property** runs the merge behind one `confirm()` that spells out the trip/contact/note counts, and one `snapshot()` so the whole thing is a single Ctrl+Z. The merge: adds the child's name as an entry in `parent.properties` (carrying `child.email` into `property.email`; folds in any sub-properties the child itself had; sets `parent.category='Hotel'` only if it was blank, so the Properties list actually shows); moves `child.contacts` onto the parent, each tagged `propertyName` = the child's name if not already set; folds the child's own top-level `contactName`/`phone`/`email` into one additional parent contact when present; unions `child.clientIds` into `parent.clientIds`; concatenates a marker note plus each of the child's `notesLog` entries (prefixed `[from <name>]`) onto `parent.notesLog`; re-points every trip where `supplierId===childId` (or, for an unlinked trip, `supplierName` matches by name) to the parent's id/name; and finally deletes the child from `db.vendors`. Trip hotel fields (`t.hotel`/`t.hotelProperty` and each `t.booked.hotel[]` entry's `hotelBrand`/`property`) are only filled when `HOTELS.indexOf(parent.name)!==-1` **and** the field is currently blank — never overwriting an existing value, and skipped entirely for a parent that isn't a recognized brand constant (its name wouldn't resolve in the `sel()`/`hotelPropertyOptionsHtml()` picklists). Ends by reopening the parent's edit form.

**Balance Due Email** (`openSupplierBalanceEmailModal(vendorId)`, the 💵 icon on each Supplier card) drafts a `mailto:` to that supplier about an outstanding balance. Important limitation driving this design: **there is no "amount owed to a supplier" field anywhere in the data model** — `totalValue`/`cashPaid` on a trip are client-facing figures (what the client paid/owes), not a supplier-payable amount, confirmed by the `invoicedToClient` comment in the Trips section above. So the Outstanding Balance ($) field is always typed in by hand; the checklist of that supplier's bookings (`getVendorStats(vendor).tripList`, same source `openVendorDetail` uses) is only a reference calculator — checking boxes updates a live "Selected total" readout, but never writes into the amount field itself, so there's nothing to silently fight a manually-typed number. The message body uses `{{bookings}}`/`{{amount}}` tokens, substituted only at send time (not live-bound to the checkboxes), so editing the message text is never overwritten by a later checkbox click — checked bookings become bullet lines (`client — destination (date) — invoice# — $value`); the amount field becomes the `{{amount}}` figure. Sending appends a `General`-type note to the supplier's own `notesLog` recording the total and booking count, then opens the `mailto:` draft the same way every other email in this app does (no server-side send capability anywhere — see the Email section's Birthday Trip Planning note for the fuller explanation of why "send" always means "open a draft"). Recipient options are the supplier's own `email` field plus every one of its Contacts that has an email.

### Vendors (`bizVendors`)
A second, deliberately separate directory from Suppliers above — `db.bizVendors`, id prefix `BV` — for non-travel operational vendors (a printer, a web host, an accountant) that have nothing to do with trip bookings, so unlike Suppliers this page carries none of the revenue/trip-matching machinery: just Name, Category (`BIZ_VENDOR_CATS` — Printing, Web/Hosting, Accounting, Legal, Marketing, Insurance, Office/Supplies, Software, Other), Phone, Website, and Notes (plain text, not a timeline). Stats: Total Vendors, Total Contacts.

**Each vendor's contacts are individually clickable right on the plain Vendors list page** — `renderBizVendors()` used to only print a truncated one-line preview (first 3 contact names, "+N more", plain text) per card; this now mirrors the Suppliers list page exactly instead: a "Contacts (N)" mini-header, a **+ Add Contact** button, and the full list of contacts, each its own clickable row (`.bizvendor-list-contact-link`) opening that specific contact's editor directly (`openBizVendorContactForm(vendorId, contactId, true)`) — same underlying contact editor the vendor's own edit-form contacts list already opened, just reachable one level higher up without opening the vendor record first. Getting here required threading a `returnToList` param through `openBizVendorContactForm()`/`saveBizVendorContact()` (previously bizVendors-only functions that always fell back to `openBizVendorForm(vendorId)` on close/save, unlike their Supplier counterparts `openVendorContactForm()`/`saveVendorContact()`, which already supported this) so Close/Cancel/Save from the list-page context returns to the plain list instead of unexpectedly landing on the parent vendor's edit form.

**Contacts work identically to Supplier Contacts** — same `{id, name, title, email, phone, notesLog}` shape, same notes-timeline + task-list modal (`openBizVendorContactForm(vendorId, contactId)`, a close copy of `openVendorContactForm`), same "+ Add Contact"/"+ Add Task" save-first behavior, same per-row delete — just under `BVC` ids (`allBizVendorContacts()`/`findBizVendorContact(id)`) and `db.bizVendors` instead of `VC`/`db.vendors`, so a Vendor Contact and a Supplier Contact can never collide even though a single task could in principle reference both.

**Website auto-syncs to a Bookmarks entry.** `syncVendorWebsiteBookmark(vendorId)`, called at the end of `saveBizVendor()`, keeps exactly one `db.bookmarks` row (audience `'Vendors'`, `category` mirroring the vendor's own, tagged `sourceVendorId` so re-saving updates it rather than creating a duplicate) in sync with the vendor's `website` field — created when a website is first set, updated (name/url/category only — any notes a user manually added to the bookmark itself are left alone) on every subsequent save, and removed if the website field is cleared out or the vendor is deleted (`delBizVendor()` also filters out any bookmark with a matching `sourceVendorId`). If a user manually deletes the synced bookmark from the Bookmarks page, saving the vendor again re-creates it — the vendor's `website` field is the source of truth, not the bookmark.

### Planner
Task list of follow-ups, most created automatically by the trip-form importer (one per new submission) or the contact-form importer (§4.5). Stats: Open Tasks, Total Tasks.

The task form's **Linked Client** dropdown is the primary contact; an **Additional Clients** checkbox list below it (same pattern as the trip form's own Additional Clients) links any number of other clients to the same task — the Client column in both the Planner list and the Dashboard's Planner card lists every linked client, each independently clickable, and the task shows up on every linked client's own task list (§2), not just the primary's.

**Additional Clients is collapsed by default** on the task form — unlike the trip form's version, which is always expanded, this one's the full `sortedClients` list (every client in the CRM, potentially hundreds) behind a one-line summary/toggle (`tk-additional-clients-toggle`/`tk-additional-clients-box`, plain show/hide, no persisted state) rather than an always-open scrolling box. The summary line (`refreshTaskAdditionalClientsSummary()`) shows whoever's currently checked, joined with `joinNames()`, and stays in sync via a `change` listener on every `.task-client-cb` — so it's accurate whether the box is expanded or not, and doesn't require expanding it just to see who's already linked.

A **View Client &rarr;** link (`#tk-client-link`, `refreshTaskClientLinkDisplay()`) sits right next to the Linked Client dropdown itself — inside the task form, not just the outer list rows — so opening a task and needing to check something on that client's own record doesn't mean closing out and searching for them separately. It only appears once a client is actually selected (blank on a fresh task with nothing linked yet), updates live on the dropdown's own `change` event, and is also populated once immediately when the form first renders — covering both a freshly-picked client and an existing task being reopened with one already linked, without needing separate code paths for each. Clicking it closes the task modal and opens that client's record directly (`closeModal(); openClientForm(cid);`, same pattern `.client-task-row` on the client's own Tasks list already uses in the other direction). The link element is always freshly created by this function rather than reused, so rebinding its click listener on every call carries none of the stacked-listener risk described above for `bindBalanceGridToggles()`.

The same pattern extends to the task form's three other linkable fields, each sharing the `taskLinkedRecordSpanHtml(btnId, label)` markup helper:
- **Linked Trip** (`#tk-trip-link`, `refreshTaskTripLinkDisplay()`) — a **View Trip &rarr;** link opening `openTripForm(tid)`.
- **Supplier Contact** (`#tk-vendor-contact-link`, `refreshTaskVendorContactLinkDisplay()`) — a **View Contact &rarr;** link. A Supplier Contact isn't its own top-level record, just an entry nested inside a Vendor's own `contacts` array (`findVendorContact()`), so "opening" one means opening that specific contact's own editor (`openVendorContactForm(vendor.id, contact.id)`) — the exact same call a Supplier's own Contacts list already uses, not the Supplier record itself.
- **Vendor Contact** (`#tk-bizvendor-contact-link`, `refreshTaskBizVendorContactLinkDisplay()`) — same idea for `db.bizVendors` (§... Vendors) instead of `db.vendors`, via `findBizVendorContact()`/`openBizVendorContactForm()`.

All four link-refresh functions are wired the same way in `openTaskForm()`: bound to their select's `change` event, plus one unconditional call right after the modal renders so an existing task reopened with something already linked shows its link immediately rather than only after the user touches the dropdown.

**Supplier Contact** (`vendorContactId`) is a separate link from **Linked Supplier** (`vendorId`) — picking a contact (searchable select) auto-selects its parent vendor into Linked Supplier too, via `refreshTaskEmailFromVendorContact()`, so the two fields can't disagree about which supplier a task is really about. It also carries the contact's own email into the task's Email field, the same way picking a client already does via `refreshTaskEmailFromLinkedClients()` — whichever was touched more recently wins, consistent with how the client-email autofill already behaves.

The Supplier Contact picklist is **scoped to the selected Linked Supplier** (`taskVendorContactOptionsHtml(vendorId, selectedId)` builds the `<option>` list): with a supplier chosen it lists only that supplier's own contacts; with none chosen it lists every supplier's contacts as "Name — Vendor" (so you can still pick a contact first — that back-fills the supplier). Changing Linked Supplier re-scopes the list (`refreshTaskVendorContactChoices()`, bound to `#tk-vendor`'s `change`) and clears the contact selection if it belonged to a different supplier. The currently-selected contact is always kept in the list even when it's from another supplier, so reopening a task whose two fields already disagree (legacy data) never silently drops the contact.

**Vendor Contact** (`bizVendorContactId`) is the same idea for `db.bizVendors` contacts — its own searchable select, its own `refreshTaskEmailFromBizVendorContact()` that carries the contact's email into the Email field. Unlike Supplier Contact there's no parent "Linked Vendor" select on the task form to keep in sync (business vendors don't have one), so this one only touches Email.

**The Planner list's Type column and its Client/Phone/Email columns are all driven by one helper, `taskContactInfo(t)`** (hoisted out of `renderPlanner()` so the Dashboard's own planner-tasks widget can apply the same precedence), with a fixed order: Marketing Plan link, then Supplier Contact, then Vendor Contact, then a Linked Supplier with no specific contact chosen, then linked client(s), then Admin (nothing linked at all) — a task explicitly about a contact should surface *their* info, not a client's that happens to also be linked. It returns a color-coded badge (`b-purple`/"Marketing Plan", `b-green`/"Supplier", `b-amber`/"Vendor", `b-blue`/"Client", `b-gray`/"Admin") for the Type column, and the `phone`/`email` it returns take priority over `linkedClientEmailsStr()`'s client-derived fallback in the Phone/Email cells. `clientLinksHtml()` uses the same precedence independently for the Client column's own label/link (falling back through `findVendorContact()`/`findBizVendorContact()` in that order before finally showing "No client linked").

**The `Type` field on the Add/Edit Task form (`t.typeOverride`) manually overrides that automatic precedence** — for a task with more than one kind of link on it (e.g. both a Linked Client and a Linked Supplier) that should read as something other than whichever wins by default. Defaults to blank ("Auto (based on linked records)"), which is a no-op — `taskContactInfo()` falls through to the automatic precedence exactly as before. Set to `'client'`/`'supplier'`/`'vendor'`/`'admin'`, it short-circuits straight to that badge, still checked *after* Marketing Plan (an auto-synced task's category isn't meant to be manually reassigned) but *before* every other automatic check. A forced `'supplier'`/`'vendor'` still sources real phone/email from an actual linked Supplier/Vendor Contact if one exists on the task (falling back to blank otherwise, same as the matching automatic branch); `'client'`/`'admin'` always leave phone/email blank, same as their automatic counterparts, relying on each caller's own client-phone fallback chain (`linkedClientPhonesStr()` etc.) to fill it in from there.

Checking a task's box (`toggleTaskDone(id, skipRender)`) saves the change immediately but updates that row in place (checked, struck through, faded) instead of fully re-rendering the list — so it stays visible and its edit/delete buttons stay reachable right after checking it, rather than instantly disappearing from the Open-tasks filter. The row drops out of view the next time the Planner page actually re-renders (navigating away and back, or changing the Open/Done filter). Delete (trash icon) always works immediately regardless.

### Assistant (floating chat widget)
A chat bubble button, fixed bottom-right on every page (not a nav section — it floats above whatever's currently open). Click it to open a small chat panel that talks to Claude through `api/claude-messages.js` on the Vercel proxy (holds `ANTHROPIC_API_KEY` server-side; the browser never sees it, same pattern as Drive/Mailchimp).

The model can only act through a fixed set of tools (`ASSISTANT_TOOLS`) — it never writes or runs arbitrary code:
- `find_clients` / `find_trips` — read-only lookups (search by name/email; filter by client, destination, status, depart-date range).
- `add_client_note`, `create_task`, `create_client` — the mutating actions. Each one calls `snapshot()` before writing, exactly like every other change in the app, so a bad or misunderstood assistant action is undoable with the same Undo button in the sidebar — there's no separate confirmation step before a tool runs.

`sendAssistantMessage()` → `handleAssistantReply()` is a standard agentic loop: send the conversation + tool defs to `/api/claude-messages`, execute any `tool_use` blocks client-side via `runAssistantTool()`, log a one-line result (✓/✗) into the chat as an `action` bubble, append `tool_result`s to the conversation, and re-call the API — repeating until Claude replies with plain text and no more tool calls. `render()` runs after every batch of tool calls so the currently-open page reflects whatever the assistant just changed. Conversation history (`assistantMessages`) is in-memory only — it resets on page reload, never written to `localStorage`.

### Clickable stat tiles (drill-down)
Every stat tile at the top of a page (Dashboard, Clients, Trips, Suppliers, Planner) is clickable and opens a modal listing the records behind that number, each row clickable through to open that client/trip/supplier/task (`openStatDrilldownModal()`). The two stats that live inside another already-open modal — Vendor Detail and Invoice Detail — instead scroll to and briefly highlight the breakdown table already shown right below them (`flashDrilldownTarget()`), since the app has a single shared modal container and can't nest a second modal on top of the first.

**Every drill-down table is sortable by clicking a column header** — ascending on the first click, descending on the second, same click-to-flip convention as the Trips/Clients/Planner page tables, with an ▲/▼ arrow marking the active column. Since a caller only ever supplies pre-rendered HTML `cells` (no separate raw values), `openStatDrilldownModal()` sorts against each cell's own rendered text (stripped of markup via a scratch element, so a cell wrapped in a styled `<span>` sorts the same as plain text would). A column sorts numerically if every non-blank cell in it, once `$`/`,`/`%` decoration is stripped, is purely a number — covering both plain counts and formatted dollar amounts with the same check — so `$500.00` correctly sorts before `$1,200.00` rather than alphabetically ("1" before "5"); everything else falls back to a case-insensitive string compare, which already sorts an ISO date string (e.g. `2026-08-27`, used throughout this app) correctly without any separate date-detection. Blank/`—` cells always sort to the end regardless of direction. Sort state resets every time the modal is freshly opened — it's local to that one `openStatDrilldownModal()` call, not persisted across reopens.

### Reports
Five tabs (`window._rptActiveTab`: `activity` / `invoice` / `certs` / `points` / `ai`):
- **Activity Report** — filter `notesLog` entries across all clients by date range, note type, and client; export to CSV or PDF.
- **By Invoice #** — filter trips by date range, supplier, and client; export to CSV or PDF. ("Invoice" here means a distinct trip/booking reference, used to avoid double-counting revenue across records that share a booking.) The date range can filter by either **Travel Date** (`departDate`) or **Invoice Date** (`invoiceDate`) — pick whichever matches what you're trying to answer, since a trip's travel date and its transaction/booking date can fall in different periods. Both dates are shown as separate columns in the results and export regardless of which one is being filtered.
- **Unused Certificates** (`getUnusedCertificatesReportData()`) — scans every client's `referralCredits` and groups the rows by `certNumber` (one certificate can have a row on more than one client's record — see the Email section below on **Referral Credit Earned**), collecting the full set of referrer names and referred names onto each group, then filters out any group where `used` is true. Optionally filterable to one referrer client; exports to CSV or PDF; clicking a row opens the first referrer's client record. Since `syncReferralCreditUsedAcrossClients()` (see below) keeps every row for a given certNumber in sync, a group's `used` flag is really one shared fact, not independent per row.
- **Combined Points** (`getCombinedPointsReportData()`) — pick any number of clients from a checkbox list ("Travelers"), and it builds one table per loyalty category (Airline Miles, Hotel Points, Cruise Line Loyalty, Car Rental Loyalty, Credit Card Points — reading `mileageBalances`/`hotelBalances`/`cruiseBalances`/`carRentalBalances`/`creditCardBalances` off each selected client, §2), each row a program with one column per selected traveler plus a **Combined Total** column summing across all of them. The point is answering "if we pool everyone's balance for the same program, is it enough" — e.g. a couple's separate Delta accounts combined. Only programs where the combined total is nonzero appear, so unused programs don't clutter the table; a category with zero qualifying programs across every selected traveler doesn't render a section at all. Exports to CSV or PDF with the same Category/Program/[traveler columns]/Combined Total shape.
- **AI Report** — type a natural-language description of the report you want (e.g. "Trips over $3,000 booked with Delta in the last year, sorted by value"), and the model decides *what to show*, never the actual figures — it calls one tool, `generate_report` (via the same `/api/claude-messages` proxy the Assistant chat widget uses, §1/§3 below — no API key in the browser), returning a `{title, filters, sortBy, sortDir, columns}` spec (see `REPORT_SPEC_TOOL`'s schema for the exact filterable fields — date range on `departDate`/`returnDate`, status, substring matches on client/destination/airline/hotel/cruise line/supplier, min/max total value, min points). `runReportSpec(spec)` then runs that spec against the **live** `db.trips` with plain deterministic filtering/sorting (`REPORT_COLUMNS`, shared with the render/export/re-run paths) — the model never sees or states a dollar figure or trip count itself, only picks the criteria, so the numbers shown are always exactly what the app's own code computes, not something the model summarized. Results render as a table (click a row to open that trip) with a CSV export. **Save This Report** (prompts for a name) persists `{id, name, prompt, spec, createdAt}` to `db.savedReports` — a saved report's **Run** button re-executes its stored spec against current data (not a frozen snapshot), so "save the report style" means saving the filter/sort/column *choices*, not a point-in-time result set.

**PDF export**: every tab's **Export PDF** button reuses the same html2canvas-into-jsPDF pipeline as the quote/certificate PDFs (`loadHtml2PdfLib()`), via a report-specific `generateReportPdfBlob()`/`reportPdfHtml()`/`downloadReportAsPdf()` (landscape letter, 1000px-wide render container — reports can run wide with several traveler columns, unlike the 650px portrait quote layout). Each tab has its own `*ReportPdfTable()` function that renders the same underlying report data (from the tab's existing `get*ReportData()`, shared with the CSV export) as a plain, self-contained HTML table — not a clone of the on-screen `.report-table`, since that has click handlers/badges not meant for print.

### Calendar
Month-grid view. Trips are painted across every day from `departDate` to `returnDate` (capped at 60 days per trip to avoid runaway rendering on bad data). Cancelled trips are excluded entirely — `renderCalendar()`'s `tripMap` build skips any trip with `status==='Cancelled'` before painting cells, so a cancelled trip shows on neither the month grid nor the day-detail modal (`openDayTripsModal`, which reads from that same `tripMap`).

### Email
A lightweight mail-merge tool: pick one or more clients, pick one of the canned templates (`TEMPLATES` in index.html — Welcome New Client, General Follow-Up, Trip Confirmation, Thank You & Referral, **Birthday Trip Planning**, **Referral Credit Earned**), preview with placeholders substituted, then send.

**"1. Select Client(s)"** is a checkbox checklist (`clientChecklistHtml('email-client-cb', ...)`, class `.email-client-cb`), not a `<select>` — picking more than one client sends *one* email addressed to all of them (comma-joined `To:`, like the referral template's referrer list below always worked), with `{{firstName}}`/`{{fullName}}` merging to a `joinNames()`-joined list ("Alice and Bob", "Alice, Bob, and Carol" — same helper the referral template's referrer/referred names use) rather than one name. `selClients` (an array, kept in sync by `bindClientChecklist()`) drives `updatePreview()`; **Select All**/**Select None** buttons above the list bulk-toggle it. The **Paying clients only**/**Subscribers only** filter checkboxes (`filteredClients()`) rebuild the checklist to just the matching subset — a client who was checked before a filter change but no longer shows up under the new filter is dropped from `selClients` too, rather than lingering as a hidden, invisible recipient. This is the same checklist pattern (and the same `clientChecklistHtml()` helper, now accepting an optional `list` param so the client checklist can pass a filtered subset while the referrer/referred checklists below keep passing the full unfiltered `sortedClients`, same as before) the referral template's Referrer(s)/Referred Client(s) checklists already used — sending to more than one recipient was already a solved problem for that one template, this just brings the same mechanism to every other template too.

**Birthday Trip Planning** is a plain mail-merge template like the first four (`{{firstName}}` only, no special send path) — what's automated is *surfacing* it, not sending it (this app has no server-side/unattended send capability anywhere; every template here ends in a `mailto:` draft the user still has to click Send on themselves). `checkForUpcomingBirthdays()` runs on the same unconditional 5-minute timer as the `checkForNew*Emails` checks (§4.4/§4.5) — unlike those three it needs no Outlook connection, since it only reads `db.clients[].birthdate` (native `<input type="date">`, so `YYYY-MM-DD`). For each client whose birthday (this year, or next year if this year's has already passed) is exactly 90 days out, it auto-creates one `db.planner` task — `title:'Birthday trip outreach — <name> (<date>)'`, `dueDate:today()`, `clientId` set, `desc` holding the *filled* Birthday Trip Planning subject+body (`fillTemplate()`) ready to paste into an email — the same task-auto-creation shape `processContactFormRow` already uses for new leads (§4.5). `mm_birthday90_notified` (a `clientId+year` set in localStorage) is the dedupe guard, since without one this would re-create the same task every 5 minutes for the entire day `daysUntil` sits at 90 (there's no per-message id to dedupe against here, unlike the email-polling checks).

Most templates use `{{firstName}}`/`{{fullName}}`/`{{email}}` against the selected client(s) and send as a plain-text `mailto:` body (mailto bodies can't carry HTML/images) — `{{email}}` specifically always resolves to the *first* selected client's email (`clients[0].email` in `fillTemplate()`), not a joined list, since it's meant for referencing one address inline, not addressing the message. **Referral Credit Earned** (`requiresReferral:true` on its `TEMPLATES` entry, no `body` string — see below) is different in every respect:

- Selecting it hides the "1. Select Client(s)" checklist entirely and relabels the same heading "1. Select Referrer(s)", showing its own checklist (`.email-referrer-cb`) in its place, plus reveals a second checklist, "Referred Client(s)" (`.email-referred-cb`) — both unaffected by the Paying/Subscriber filters (they always pass the full `sortedClients` to `clientChecklistHtml()`, unlike the main client checklist). Picking the same client as both a referrer and a referred client shows an inline warning instead of sending a nonsensical email.
- **$100 referral bonus certificate**: exactly **one** per send, regardless of how many referrers or referred people are selected — `referralCertificateHtml()` shows the Miles Man logo, every selected referrer's name joined onto the "issued to" line (`joinNames()` — "Aaron and Alice", "Aaron, Alice, and Sam"), a unique sequential number, and fixed terms text (good for $100 off next booking fees/trip cost; a trip means a unique booking record number; no value once redeemed; non-transferable but usable when booking a trip for someone else via the referrer's own miles/points/credit card).
- **Referral credit rows still track per (referrer, referred person) pair**: `addReferralCreditEntries()` still writes one `referralCredits` row (§2) per referrer per referred person onto each referrer's own client record, so e.g. 2 referrers together referring 2 people is 4 credit rows — but all 4 share the *same* `certNumber`, since only one certificate was actually issued for the whole send. Because more than one client's record can hold a row for the same certNumber, checking (or unchecking) a row's "Used" box and saving that client propagates the same used/unused state onto every other client's row sharing that certNumber (`syncReferralCreditUsedAcrossClients()`, called from `saveClient()`) — a certNumber's used status is one shared fact, not independent per client.
- **Certificate numbering**: a single ever-increasing counter, `localStorage['mm_next_certificate_number']` (starts at 1, never reused, never reset). `peekNextCertificateNumber()` reads it for preview display without advancing it; `consumeCertificateNumbers(1)` is the only thing that actually advances it, and only runs once per send — `renderReferralCreditPreview()`'s `finalize()` memoizes the result so clicking both "Open in Outlook" and "Log as Note" (or either twice) for the same preview doesn't burn an extra number or double-add credit rows. Previewing/reselecting clients never consumes a number, only an actual send/log does.
- **Sending mechanics differ from every other template here**: because the certificate embeds a logo image, this can't go out as a plain mailto: body. `renderReferralCreditPreview()` builds styled HTML (`referralCreditEmailBodyHtml()`) and copies it to the clipboard (`copyHtmlToClipboard()`, same technique Email Quote/Itinerary use) before opening a subject-only `mailto:` for pasting into Outlook.
- **PDF "attachment"**: a `mailto:` link has no way to attach a file automatically (true of every email client, not a limitation specific to this app). Clicking "Open in Outlook" also renders just the certificate (`certificatesPdfHtml()`, via the same `generateQuotePdfBlob()` used for quote PDFs) and triggers a browser download (`downloadPdfBlob()`) named `Referral-Certificate-<number>.pdf` — the closest real equivalent to an attachment, with a toast telling the user to attach the downloaded file manually. "Log as Note" doesn't download a PDF (no email is actually being opened on that path).

**Net Rate Hotel Voucher** — a related but separate feature, not reached from the Email menu at all: a "🧾 Net Rate Voucher" button sits on every hotel entry row inside a Trip's **Booked Trip Details → Hotel** section (`hotelEntryRowInnerHtml()`). Clicking it (`createNetRateHotelVoucher()`) reads that one row's current on-screen values directly (`readHotelEntryRow()` — hotel brand/property, confirmation number, check-in date, nights, notes; no need to Save the trip first) plus the trip's currently-selected guest(s) (`currentTripGuestNames()` — the primary Client dropdown plus any checked Additional Clients, joined with `joinNames()`), and builds a standalone printable/emailable voucher (`hotelVoucherHtml()`, visually the same Miles Man logo + double-blue-border card as the referral certificate above, with its own `mm_next_voucher_number` sequential counter — same `peekNextVoucherNumber()`/`consumeVoucherNumbers()` pattern as certificate numbers, never reused). The voucher states plainly that the room has been prepaid to Miles Man at a net/wholesale rate, asks the hotel not to disclose that rate to the guest, and notes the guest is responsible only for incidental charges — the whole point of a document meant to be handed to a front-desk agent, not the client's own copy of what they paid. Checkout date is computed (`addDaysToDateStr(checkInDate, nights)`) rather than stored, since Booked Trip Details' hotel entries never carry one directly. Same two-birds send mechanic as the referral certificate: `copyHtmlToClipboard()` puts it on the clipboard for pasting into an email, and `generateQuotePdfBlob()`/`downloadPdfBlob()` triggers a `Hotel-Voucher-<number>.pdf` download — there's no dedicated Send/Log flow beyond that, since this isn't tied to `TEMPLATES`/`fillTemplate()` at all, and no client note gets logged automatically (this document is meant for the hotel, not a record of client communication). **`VOUCHER_AGENCY_PHONE`/`VOUCHER_AGENCY_EMAIL` ship blank** — until filled in, the voucher's contact line shows a placeholder telling whoever's reading the source where to add them, rather than fabricating one.

There are two **separate**, more elaborate modals reached from header buttons in the Email menu:

- **Email Quote** (`openEmailQuoteModal`) — purpose-built for building line-itemized cruise pricing quotes by hand. `QUOTE_TEMPLATE_LINES` lists which cruise lines get a full styled HTML template (header/hero/pricing table/included-items/payment-terms) instead of the generic plain-text fallback every other cruise line uses: **Virgin Voyages, Princess, Royal Caribbean, Ritz Carlton Yachts, Seabourn, Explora Journeys, Windstar**. Virgin Voyages and Princess have their own named cabin-tier/fare-tier/add-on structure (`QUOTE_CRUISE_CONFIG`); the other five (Royal Caribbean, Ritz Carlton Yachts, Seabourn, Explora Journeys, Windstar) share one generic Cabin/Suite Category + Total Price + Insurance + Add-ons structure — the row *labels* are generic, but of these five, Ritz Carlton Yachts/Seabourn/Explora Journeys/Windstar now populate real named cabin/suite categories in that Cabin Category column too (via `QUOTE_CRUISE_CONFIG`'s `cabinTypes`, the same lists §2's `booked.cruise.cabins` uses), while Royal Caribbean still falls back to generic Interior/Window/Balcony/Suite since it has no `QUOTE_CRUISE_CONFIG` entry of its own. Each of the seven has its own `xxxQuoteOpts()`/`xxxQuoteBodyHtml()` duo (the third member of what used to be a trio, `xxxQuoteHtml()`, was removed once nothing called it any more — see the multi-date bullet below for why) and its own "what's included" copy — the three ultra-luxury lines (Ritz Carlton Yachts, Seabourn, Explora Journeys) are all-inclusive, so their included-items lists reflect that (all-suite, all dining, beverages including spirits, gratuities, WiFi); Windstar isn't an all-inclusive line, so it uses Royal Caribbean's non-inclusive Cabin Category structure and included-items copy (main dining, onboard entertainment, stateroom) instead.
  - **Logos**: the header shows the Miles Man logo plus (when set) the cruise line's own logo, via a `cruiseLogoDataUri`/`Width`/`Height`/`Alt` set of opts — falls back to Miles Man logo only if empty. Virgin Voyages, Princess, and Royal Caribbean logos were rasterized from Wikimedia Commons SVGs (`XXX_LOGO_DATA_URI` constants). Seabourn's is a low-resolution (452×190) PNG from Commons uploaded by a third party under CC0, not an official Carnival/Seabourn release — usable but lower quality/shakier provenance than the other three. **Ritz Carlton Yachts, Explora Journeys, and Windstar have no logo** (`''` placeholder) — nothing usable exists on Wikimedia Commons for any of the three (nothing at all for the Yacht Collection; the only Explora Journeys and Windstar copies found are Wikipedia non-free/fair-use content, not legally reusable in a commercial email) — all three fall back to Miles Man logo only until an official logo file is sourced from the brand's own press/media kit.
  - **PDF saved to Drive**: every sent quote (styled-template or plain-text) also gets rendered client-side to PDF (`generateQuotePdfBlob()`, via `html2pdf.js`) and uploaded fire-and-forget to a "Miles Man Quotes" Drive folder (`DRIVE_QUOTES_FOLDER_NAME`), named `<client name>.<cruise line>.<sailing date>.pdf` (falls back to `Quote` for a missing client/cruise line, or today's date for a missing sailing date). Silently skipped (with a toast) if Google Drive isn't connected — never forces a login redirect mid-send.
  - **Gratuities & Voyage Protection** (`eq-gratuities`/`eq-voyage-protection`) — two optional free-text amount fields, always shown (not gated behind `QUOTE_TEMPLATE_LINES`/`eq-template-fields` the way Itinerary/Deposit/Payment Deadline are), since every cruise line's quote can carry these two figures. Deliberately a single total for the whole quote rather than per-cabin columns — Virgin Voyages already has its own per-row `Gratuities`/`Insurance` columns in `QUOTE_CRUISE_CONFIG` (§ above) for when gratuities genuinely differ by fare type, and this doesn't touch that; it's for the common case of one blanket figure. Read into `meta.gratuities`/`meta.voyageProtection` (so every styled template's `Object.assign({...defaults}, meta)` picks it up automatically, rendered as its own line — `<strong>Gratuities:</strong> $…` / `<strong>Voyage Protection:</strong> $…` — right after "What's included" and before Additional Notes, only when at least one is filled in) and also onto `collectQuoteData()`'s top-level return value (`d.gratuities`/`d.voyageProtection`) for the plain-text fallback body and the logged client note, the same dual top-level-plus-meta pattern `ship` already uses.
  - **Multiple dates in one email** — **+ Add Another Date to This Quote** (`eq-add-date`) snapshots the current form (a full `collectQuoteData()` call — cruise line/ship/dates/pricing/notes/gratuities/everything) into a `savedOptions` array local to the modal's closure, then clears just Sailing/Return Date and every `.quote-cell` so the next date can be entered; a running list (`#eq-saved-options`, `renderSavedOptionsList()`) shows what's been added so far with a Remove button per row. Nothing about this requires staying on the same cruise line — each saved option is a fully independent `collectQuoteData()` snapshot, so mixing e.g. a Royal Caribbean date with a Carnival date in the same email works with no special-casing.
    - **`buildAllOptions()`** is what Preview and Send both call instead of `collectQuoteData()` directly — it combines `savedOptions` with whatever's currently on the form (only if the pricing grid actually has something entered; a `silentIfEmpty` flag on `collectQuoteData()` keeps an intentionally-blank trailing form from throwing a spurious "Select a cruise line" error once at least one option is already saved) and returns the full list. With zero saved options this reduces to exactly `[collectQuoteData()]` — the single-quote case behaves byte-for-byte as it did before this feature existed.
    - **Rendering**: `quoteOptionBodyHtml(d)` picks `buildTemplateBodyHtml(d)` or the plain fallback (`plainQuoteBodyHtml(plainQuoteBodyParts(d), ...)`, both `plainQuoteBodyParts()` and this function newly extracted from what used to be inlined once in the send handler) per option, and `all.map(quoteOptionBodyHtml).join('')` stacks them — each is already a complete, self-contained 600px white card (logo/greeting/pricing/what's-included/deposit terms/sign-off), so concatenating them just reads as separate cards stacked on the shared grey background, no extra wrapper markup needed. `labelOptionsIfMultiple()` only sets `d.meta.optionLabel` (rendered as a small blue pill at the top of the card, or as a plain `— Option N: <date> —` text divider in the plain-fallback case) when `all.length>1` — a single quote never shows an "Option 1" label it doesn't need. Preview wraps the combined body in the shell via the newly-extracted `wrapEmailShell(bodyHtml, docTitle)` (factored out of `quoteEmailShellHtml()`, which still exists as a thin wrapper for anything calling it with a single `opts` object) — this incidentally means Preview now works for plain-fallback cruise lines too, which it never supported before (Preview used to hard-block anything outside `QUOTE_TEMPLATE_LINES`).
    - **Sending**: subject becomes `"<cruise line> Cruise Quote — N Date Options"` (or just `"Cruise Quote — N Date Options"` if the options don't share a cruise line) instead of the single-quote subject; the combined HTML is copied to the clipboard and a subject-only `mailto:` opens, exactly the styled-template send path already used — so a multi-date send always uses the clipboard-copy path even if every option happens to be a plain-fallback line (the single-plain-line case, `all.length===1` and not a `QUOTE_TEMPLATE_LINES` cruise line, is the only one still using the old direct `mailto:body=` param with no clipboard step). One combined PDF (`saveQuotePdfToDrive`, filename based on the first option) and **one** client note (`logQuoteNote(all, subject)` — always takes the options array now, with `— Option N: <date> —` dividers between each option's lines when there's more than one) get produced per send, not one per option — a client comparing three dates in one email generated one email, so it's logged as one activity entry.
- **Email Itinerary** (`openEmailItineraryModal`) — pick a client, pick one of their actual `db.trips` records, and it generates a styled HTML recap straight from whatever that trip has filled in: dates, passengers, booking reference, supplier, points/total value, trip notes, plus a section per Booked Trip Details category — every section is conditional on the trip actually having that data, so e.g. a flight-only trip shows no Train/Bus/Car Rental/Tours/Theme Park/Cruise/Hotel boxes at all. **Confirmation / Booking Ref** (the trip's Invoice Number) only shows in the Booking Details box when the trip has no Supplier linked — same `invoicedToClient` rule `bookedTripSummaryHtml()` already uses (§2): a linked Supplier means the invoice went to that supplier, not the client, so surfacing "the" invoice number on this client-facing email would be misleading. **Points Used** and **Total Trip Value** are deliberately sourced from Booked Trip Details (`tripBookedPoints()`/`tripBookedPriceTotal()` — the latter sums every category's own `price` field) rather than the trip's top-level `pointsUsed`/`totalValue`/`cashPaid`, since those get set directly from the revenue import and aren't meant to be quoted back to the client; there's no "Amount Paid" row at all, since `cashPaid` has no Booked Trip Details equivalent to fall back to instead. The opening line ("Here's your itinerary for ___!") uses `booked.tripName` when set, falling back to the trip's `destination` otherwise — the rest of the email (the "Destination" detail row, subject line, PDF filename) still uses `destination` regardless, so setting a Trip Name only changes that one greeting sentence.
  - **Overview row "Passengers"**: every client linked to the trip — `trip.clientId` (the primary/billing contact) plus every id in `trip.clientIds` (additional travelers) — resolved to names and joined with `joinNames()`. "Trip Type" and "Status" were removed from this overview section per request.
  - **"Also Part of This Vacation"** — one row per `trip.linkedTripIds` entry (see §2), right after the Overview box: the linked trip's `booked.tripName` (falling back to its `destination`) as the label, its own depart/return dates as the value (falling back to its `destination` if it has no dates at all). Only rendered when the trip actually has linked trips — like every other section here, an empty `linkedTripIds` means no box at all rather than an empty one.
  - **Provider logos**: each detail box's `itineraryDetailBox(title, rowsHtml, logoSrc)` takes an optional third argument — a data URI or plain URL — rendered as a small image to the left of the box title. Each Airline Record box looks up `AIRLINE_LOGOS[...]` keyed by that record's **first flight segment's** airline (or `AIRLINE_LOGOS[opts.airline]` for the no-records fallback) — one logo per record box, not per individual segment, since a record's segments are usually all the same carrier; Hotel boxes look up `HOTEL_LOGOS[h.hotelBrand]` per entry the same way; the Car Rental box uses `CAR_RENTAL_LOGOS[opts.carRentalCompany]`. `AIRLINE_LOGOS`/`HOTEL_LOGOS`/`CAR_RENTAL_LOGOS` are name-keyed objects of `data:image/svg+xml;base64,...` URIs, sourced under the same strict free-license-only rule as the cruise line logos (Wikimedia Commons PD-textlogo license only, never a Wikipedia fair-use infobox image). Populated for: all 18 `AIRLINES` entries (several — Delta, JetBlue, ANA, British Airways, Air Canada, Alaska/Hawaiian Air, Air France, Virgin Atlantic, JAL, United, Qantas — only have a free wordmark/historic-era file, not the airline's current full pictorial logo, since that's all Commons had under a qualifying license); `HOTELS` except **Four Seasons** (no Commons file at all) and **Ritz-Carlton** (the only Commons file is CC-BY-SA, which fails the no-share-alike rule); `CAR_RENTALS` except **Dollar** (same CC-BY-SA issue, and the file is a low-res GIF, not SVG). A brand missing from the object (no free logo exists, or wasn't sourced) just renders with no logo. Train and Bus have no fixed company list to look a logo up by (both sections are free-text departure/arrival city fields), so they instead get a manual **Logo URL** field on `booked.train`/`booked.bus` (`tra.logoUrl`/`bus.logoUrl`) — paste any image URL and it's used as-is, no lookup involved. Suppliers (`db.vendors`) intentionally have no logo mechanism at all — they're user-created records with no fixed identity to source a logo for.
    - **Cruise box** uses its own `CRUISE_LOGOS[opts.cruiseLine]` lookup, keyed by the exact `CRUISE_LINES` name — **not** `getQuoteConfig()`/`QUOTE_CRUISE_CONFIG` (§3's cabin/pricing config for Email Quote, which never carried a logo at all; that mismatch meant no cruise logo ever rendered here until this lookup was added). Populated for 8 of the 14 `CRUISE_LINES`: Virgin Voyages, Princess, Royal Caribbean, Seabourn (reusing the same `*_LOGO_DATA_URI` constants Email Quote's styled templates use, §3), plus Norwegian, Celebrity, Disney Cruise Line, and MSC Cruises (sourced fresh for this lookup — all four are PD-textlogo/PD-ineligible wordmarks on Commons). Blank for **Carnival** (its real "whale tail" mark is pictorial/copyrightable, only exists as a Wikipedia non-free file), **Holland America** (no Commons file at all), **Viking** (the only Commons file is CC-BY-SA, rejected), and **Ritz Carlton Yachts/Explora Journeys/Windstar** (same as §3 — nothing free-licensed exists for any of the three).
  - **Flight/Hotel/Cruise prefer Booked Trip Details over the trip's simpler top-level basic fields**, matching how Car Rental/Tours/Theme Park/Train/Bus already worked: if `booked.airline.records` has entries, one "Airline Record" box is built **per record** (titled "Airline Record 1"/"Airline Record 2" etc. once there's more than one) — Record Number and Passengers (that record's own `passengerClientIds`, resolved to names) up top, then that record's own flight segment(s) below, each segment's rows prefixed "Flight N:" only when the record itself has more than one segment; only falls back to the single `trip.airline`/`trip.origin`/`trip.destination`/`trip.flightClass`-based summary when there are no records at all. Likewise `booked.hotel[]` entries each get their own "Hotel Details" box before falling back to `trip.hotel`/`trip.hotelNights`; `booked.cruise` fields (Cruise Line, Ship, Sailing Date, Nights, Departure Port, Confirmation Number, Loyalty Number, plus a row per `cabins[]` entry) enrich the single Cruise Details box, still falling back to `trip.cruiseLine`/`trip.shipName` if `booked.cruise` has nothing.
  - **The basic-fields fallback for Flight Details specifically excludes `flightClass` on its own** — `saveTrip()` defaults `flightClass` to `'Economy'` even on a trip with zero flight info, so that field alone can't signal "this section is actually completed"; the fallback box only renders when `trip.airline` or `trip.origin` is also non-empty.
  - Since `booked.tours` is an array, each tour entry gets its own "Tour Details" box (titled "Tour 1 Details", "Tour 2 Details", etc. once there's more than one). Reuses the same header/branding shell as Email Quote.
  - **PDF saved to Drive**: same fire-and-forget pattern as Email Quote's (`generateQuotePdfBlob()`), but into its own **"Miles Man Itineraries"** Drive folder (`DRIVE_ITINERARIES_FOLDER_NAME`/`getOrCreateDriveItinerariesFolder()`/`saveItineraryPdfToDrive()`) rather than "Miles Man Quotes" — an itinerary is a confirmed-booking recap, not a pricing quote, so the two document types don't mix in one folder. Named `<client name>.<destination>.<depart date>.pdf` (falls back to `Itinerary` for a missing client/destination, or today's date for a missing depart date). Silently skipped (with a toast) if Google Drive isn't connected — never forces a login redirect mid-send.

Both share the same send mechanics: the rendered HTML is copied to the clipboard (`copyHtmlToClipboard()` — `mailto:` bodies are plain-text only) and `mailto:` is opened to the client's address for pasting into Outlook, then an `Email Sent` note is logged on the client record.

### Marketing
`renderMarketing()` — a Facebook Ads card, a Canva connect card, a **Marketing Plan** card, and a **Marketing Calendar** card. See §4.8 for the Facebook Ads OAuth/API mechanics; this is the page layout.

**Marketing Plan** (`db.marketingPlan`, `MP` ids) is a lightweight scheduled-activity list — each item is `{title, channel, date, status, notes}`, separate from the Planner's client/trip-linked tasks. `MARKETING_PLAN_STATUSES` = Planned / In Progress / Done / Cancelled. Every item with a date also appears on the Marketing Calendar below (shared `MARKETING_CHANNEL_COLORS`), and `syncMarketingPlanTask()` upserts one matching Planner task per item (keyed by `marketingPlanId`). `+ Load 30-Day Calendar` seeds `DEFAULT_MARKETING_PLAN` (title-deduped); a first-run auto-seed does the same silently. The `✨` per-row button drafts that item's content with Claude (`draftMarketingPlanItemWithAI()` → `marketingAiDraftRequest()` → the `api/claude-messages` proxy), shown in a review modal (`renderMarketingAiDraftModal()`) — editable textarea, **Copy**, **Save to Item Notes**, plus an **"Ask the AI to revise"** box (type what to change → re-runs the request as a follow-up turn: prior draft + instruction → new draft, modal re-renders). For **Blog Post**-channel items only, a **"Save as WordPress Draft"** button (`saveMarketingDraftToWordPress()`) POSTs the draft to `https://<WP_SITE>/wp-json/wp/v2/posts` as `status:'draft'` using the same Application Password `getJetpackSubCreds()` stores (Analytics tab → "Set Up Auto-Subscribe"); it never publishes, opens the wp-admin editor on success, and remembers the new post's id on the item (`wpDraftId`) so a second save updates that draft instead of creating a duplicate (falling back to a fresh create if the remembered post was trashed/published). Each list row has a **completion checkbox** — an item counts as complete when `status === 'Done'`, and the checkbox is a fast toggle for that (`toggleMarketingPlanDone()`: checking sets `Done`, unchecking sets `Planned`; a completed row's date/title dim to 55% opacity). The card header's **Hide completed** checkbox filters Done items out of the list and is **ON by default** (`window._mktPlanHideDone !== false` means hide — the same `!== false` convention the collapse toggles use, so an untouched session starts filtered; session-scoped); `marketingPlanItemComplete(item)` is the shared predicate.

Shows a **Connect Facebook Ads** button until connected (`mm_fb_token` in localStorage; **Disconnect** clears it). Once connected, `loadFacebookCampaigns()` lists every campaign (name, status badge, objective, daily/lifetime budget, last-30-days spend/impressions/clicks/CPC via a parallel `insights` call) with a **Pause**/**Activate** toggle per row (`confirm()`-gated before activating, since that starts real spend immediately) and a **+ Create Campaign** button opening a 4-step wizard: Campaign (name/objective/special ad category) → Ad Set (budget/start date/country/age range/gender) → Creative (Facebook Page, ad copy, image upload, destination URL, call-to-action) → Review & Launch. Every object the wizard creates — campaign, ad set, ad creative, ad — is created with `status:'PAUSED'`; nothing spends money until explicitly activated afterward via the same toggle used on the campaign list. Field shapes follow Meta's documented Marketing API behavior; any validation error Facebook returns is shown verbatim in the wizard's progress panel rather than swallowed, the same show-the-real-error approach used elsewhere in this app for an integration whose exact response shape hasn't been independently reconfirmed against a live create.

**Graph API errors are logged in full to the Debug Panel**, not just shown on screen. The Facebook Ads card only ever displayed Meta's short `message` (e.g. `"API Access Blocked"`, which almost always means the app hasn't been through Meta's App Review for Marketing API permissions, or the Business Manager owning the ad account hasn't completed Business Verification) and discarded the rest of the error object — but Meta's errors also carry a `code`/`error_subcode`/`type`/`fbtrace_id` that actually pinpoint the cause. `fbLogGraphError(context, err)` logs all of it (account fetch, campaigns fetch, insights fetch, and the Pause/Activate toggle) to the Debug Panel, and the two `catch(e)` branches that previously only updated the screen now also log the raw JS error message — a request that never got any response at all (network down, CORS rejection, an ad blocker silently dropping the call) is logged separately from a Facebook-returned error object, since those are meaningfully different failure modes.

### Analytics
Seven independent data sources, each its own card in this order — **WordPress.com / Jetpack Stats**, **Google Analytics (GA4)**, **Facebook** (Ads/Page/Instagram — one card, three subsections, §4.8), **X** (§4.10), **TikTok** (§4.11), **Mailchimp**, then **SEO (Yoast)**. See §4.7/§4.9 for the OAuth/proxy mechanics behind the first two and last one; this section is the user-facing page layout.

**Daily Summary / "Yesterday's Analytics"** (`loadDailySummary()`, two cards at the very top of the Analytics tab and also shown on the Dashboard — both read/write the exact same `#daily-summary-body`/`#daily-compilation-body` containers and the same per-day `localStorage` cache, so whichever page loads first generates it and the other just displays the cached result, no duplicate Claude call): pulls one day's worth of numbers from every connected source in parallel (`Promise.all` of per-source `fetchYesterday*()` calls, each independently try/caught — one source failing or being disconnected never blocks the others) and shows them two ways. **"Yesterday's Analytics"** (`dailyCompilationHtml()`) is the raw compiled numbers, one mini stat-grid per connected source, computed client-side with no AI involved. **Daily Summary** sends that same compiled JSON to Claude (`api/claude-messages.js`) with a system prompt asking for a 2-3 sentence summary, 2-4 notable observations, and 1-3 concrete actions — written for a non-analyst small-business owner, explicitly told not to manufacture insight from small-number noise or hand out generic advice.

Cached per-day under `mm_daily_compilation_<date>`/`dailySummaryCacheKey()`; the **Regenerate** button (`force:true`) bypasses that cache and re-fetches everything, including a fresh Claude call.

**Not every source has a genuinely day-specific number, and the framing has to say so or the AI summary will describe a running total as if it were yesterday's activity** — this exact mistake is what an earlier Mailchimp mislabeling (a "Total Unsubscribed" figure that could only ever grow, sitting right next to a real daily one) corrected once already; it's since been removed outright rather than just relabeled, once a real day-specific replacement existed. GA4/WordPress/Facebook Ads/Facebook Page/Instagram all have real Insights-style day-scoped endpoints. Mailchimp, X, TikTok, and SEO don't (or only partly do), so each handles it differently:
- **Mailchimp** (`fetchYesterdayMailchimpSummary()`) is now fully day-specific/latest-send-specific rather than blending in a cumulative figure: `Subscribers Added Yesterday`/`Unsubscribed Yesterday` (real day-specific, via `countMailchimpSubscribersAddedOnDate()`/`countMailchimpUnsubscribesOnDate()`) plus `Open Rate (latest email)`/`Click Rate (latest email)` — the single most recently sent campaign's own rates (`GET /reports?...&count=1`), not a list-wide average — same underlying data the interactive Mailchimp stat tiles use (`loadMailchimpStatsTiles()`, below).
- **X** reuses `xFollowerSnapshot()`'s existing once-per-calendar-day cache (`fetchYesterdayX()`, §4.10) — free in terms of X's per-request billing, since it's the same cached read the X card and Dashboard tile already share. Its `Change` figure is a real day-over-day delta from two cached snapshots, labeled with the actual comparison date rather than assumed to be literally yesterday (§4.10's `xPreviousSnapshot()` note).
- **TikTok** (`fetchYesterdayTiktok()`) and **SEO** (`fetchSeoAuditSummary()`, reusing `loadYoastSeoAudit()`'s own counting logic) have no day-specific data at all — TikTok's Display API only exposes current totals, and the SEO block is a completeness audit of whatever posts/pages exist right now. Both get an explicit non-daily label in two places at once: the block title on screen (`"TikTok (current totals)"`, `"SEO (Yoast) — site audit"`) and the source label sent to Claude (`labelByKey`'s `tiktok`/`seo` entries append `", not day-specific"`), on top of a system-prompt instruction telling the model never to phrase a labeled-non-daily source as "yesterday you gained/lost X." Belt-and-suspenders — the on-screen label protects a human reading the compiled numbers directly, the AI-facing label and prompt instruction protect the generated prose.

**WordPress.com card**: shows a **Connect WordPress.com** button until connected (`mm_wp_token` in localStorage — a **Disconnect** button clears it), then `loadWordpressStats()` renders stat tiles (Visitors/Views today, yesterday, all-time; **Blog Followers**), a best-day callout, a "Most recent" one-line summary of the latest date in the 30-day feed (always visible), and the full Last 30 Days table (date/views/visitors, most-recent first) behind a collapse toggle — **collapsed by default**, same `inlineCollapseHeaderHtml()`/`analyticsSectionCollapsed('wp-daily-table')` mechanism described below for GA4. The **Blog Followers** tile itself is clickable (`#stat-wp-followers-tile`) — since it's a plain number and not obviously part of the drill-down section below it, clicking it expands and scrolls to that section (`window._analyticsCollapsed['wp-followers']=false; render();`) rather than leaving the user stuck on a non-interactive number sharing a label with the real interactive one further down.

**GA4 card**: no separate connect button — it reuses the same Google login Drive backup already uses (`getDriveTokenSilent()`, §4.1). If Drive was never connected, or was connected before the `analytics.readonly` scope existed, it shows a **Connect**/**Reconnect Google Drive** button instead of silently failing. Once connected, `loadGA4Stats()` renders stat tiles (Active Users/Page Views/Sessions, last 30 days) and a daily breakdown table.

**SEO (Yoast) card** needs no connect step at all — unlike the other two cards, it's public data (§4.9), so `loadYoastSeoAudit()` fetches it directly on page load. A 4-tile summary (Posts & Pages / Missing Description / Noindexed / Missing OG Image) sits above two collapsible sections, **Posts** and **Pages** (fetched together in one call, since posts+pages both feed the same summary tiles regardless of which section is expanded — see the Drill-down bullet below), each auditing that type's Yoast metadata (`yoast_head_json`: SEO title, meta description, `robots` noindex flag, OG image) against Yoast's own length guidance: an SEO title over 60 characters, a meta description over 156 characters or missing entirely, an accidentally-noindexed page, or a missing OG image. This is metadata-*completeness* auditing, not Yoast's own internal green/amber/red SEO score — that score is derived from post meta (`_yoast_wpseo_linkdex`/`_yoast_wpseo_content_score`) only exposed to an authenticated wp-admin session, never the public REST API, so it can't be reproduced here; this instead surfaces the same underlying signals (title/description length, indexability, social image) the score is partly built from.

**Facebook card** (not one of the three cards above, but on the same Analytics tab — shows/hides with the same **Connect Facebook**/**Disconnect** button the Marketing tab's Facebook Ads uses, §4.8, since it's the same OAuth connection): three subsections. **Ads Performance** (`loadFacebookAdsAnalytics()`) — spend/impressions/clicks/reach over the last 30 days for `FB_AD_ACCOUNT`, plus an expandable **Daily Spend & Performance** breakdown. **Page Performance (organic, non-ads)** (`loadFacebookPageAnalytics()`) — Page Likes (all-time, from the Page object's `followers_count` field, not Insights), Page Views/Impressions/Reach/Post Engagements (last 28 days, from Page Insights). **Instagram (via connected Page)** (`loadInstagramAnalytics()`) — Followers/Posts (all-time, from the linked IG account object) and Reach/Views/Profile Views (last 28 days, from IG Insights) — see §4.8 for the full mechanics of how the IG account is found and why some of its metric shapes aren't yet confirmed against a live response.

**X card** (`loadXAnalytics()`): shows a **Connect X** button (plus an inline per-read cost warning) until connected, then four stat tiles — Followers (with a delta line under it), Following, Posts, Listed — from a single `GET /2/users/me?user.fields=public_metrics` read, plus a locally-built **Follower History** table. Everything here comes from `xFollowerSnapshot()`'s once-per-calendar-day cache (§4.10); the header states which date the shown snapshot is from and whether it was cached, and a **Refresh now** button forces a fresh (billable) read. The history table is built purely from accumulated local snapshots — no API calls, no cost — and says so rather than showing an empty table until at least two days have been recorded. **Disconnect** clears the tokens but deliberately keeps `mm_x_follower_history`, since that trend data cost real money to accumulate and reconnecting should resume it rather than restart from zero.

**TikTok card** (`loadTiktokAnalytics()`): shows a **Connect TikTok** button (plus a note that it needs a production-approved TikTok app) until connected, then four stat tiles — Followers, Following, Likes, Videos — from a single `GET /v2/user/info/` read, refetched on every render (no cache needed, §4.11: unlike X this is a free API). `tiktokUserInfoValue()` handles TikTok's error convention, which wraps *everything* — including success — in `{data, error:{code,message,log_id}}`, with `error.code` the literal string `'ok'` on success rather than the field being absent; checking that instead of plain truthiness is what lets a real TikTok error surface correctly rather than either being missed or false-triggering on every response. **Disconnect** clears the connection. TikTok does appear in the Daily Summary / "Yesterday's Analytics" compilation above, but only as an explicitly-labeled current-totals snapshot (`"TikTok (current totals)"`) rather than framed as day-specific activity — see that section's own breakdown of which sources have real daily data and which don't.

**Mailchimp card** (`loadMailchimpAnalytics()` — not one of the three cards above, but on the same Analytics tab): shows a **Choose Mailchimp Audience** button until one's picked, then delegates its six stat tiles to the shared `loadMailchimpStatsTiles(elId, opts)` — **Subscribers**, **Subscribers Added Yesterday**, **Unsubscribed Yesterday**, **Campaigns Sent**, **Open Rate**, **Click Rate** — reused as-is by the Dashboard's own Mailchimp card below (`opts.showListName`/`opts.onCampaignsClick` are the only two things that differ per caller — see the Dashboard section). Total Unsubscribed (a cumulative, all-time count that could only ever grow) was removed as redundant with the day-specific Unsubscribed Yesterday tile below it.

**Unsubscribed Yesterday** and **Subscribers Added Yesterday** are both real day-specific counts (Mailchimp's List stats endpoint has no date-range parameter at all, so neither can come from there) — `countMailchimpUnsubscribesOnDate(listId, dateStr)` and `countMailchimpSubscribersAddedOnDate(listId, dateStr)` fetch `/lists/{id}/members?status=unsubscribed&sort_field=last_changed...` / `?status=subscribed&sort_field=timestamp_opt...` respectively (sorted newest-first) and count how many members' date field matches yesterday, stopping as soon as they scan past it. `timestamp_opt` is when a member confirmed opt-in; on a single-opt-in audience (no separate confirmation step, the common case) Mailchimp sets it to the same moment as signup, so the count works either way. Both tiles open the same **Subscribers**/**Unsubscribed** drill-down modal (`openMailchimpMembersModal()`) as their non-"Yesterday" siblings.

**Open Rate** and **Click Rate** are the *most recently sent campaign's own* rates — not a list-wide average — fetched via `GET /reports?list_id=...&count=1&sort_field=send_time&sort_dir=DESC` (the same single-campaign fetch `loadLatestMailchimpCampaignSummary()` uses for its own summary line, §4.3's Recent Campaigns note) and converted from the Reports endpoint's fraction convention (`0.4956` meaning 49.56%) — the *opposite* of List stats' own `open_rate`/`click_rate`, which are already percentages; Mailchimp isn't consistent about this across endpoints. Clicking either tile opens that same latest campaign's `openMailchimpCampaignActivity()` drilldown directly.

**Drill-down detail sections**: each card has collapsible sub-sections (`analyticsSectionHtml()`/`analyticsSectionCollapsed()` — default collapsed, same collapse-state-object pattern Bookmarks' category headers already use).
- **WordPress** (five sections, all fully formatted, field names confirmed against real responses): **Top Posts & Pages** (`loadWordpressTopPosts()` — title linking out to the page, type, views, sorted desc; `summary.postviews[]`). **Referrers** (`loadWordpressReferrers()` — source name/URL + total, `summary.groups[]`; each group's own top-level `total` is used rather than digging into its `results` field, which inconsistently comes back as either an array of sub-sources or a bare `{views:N}` object depending on the group). **Views by Country** (`loadWordpressCountries()` — full country name + flag icon + views, `summary.views[]` joined against the `country-info` lookup for the display name). **Search Terms** (`loadWordpressSearchTerms()`) has its outer shape confirmed (`summary.search_terms[]`/`encrypted_search_terms`/`other_search_terms`/`total_search_terms` — the real response had an empty array, since most search engines encrypt the query before referring traffic, which the empty-state message surfaces via those counts), though individual-entry field names (`term`/`views`) are inferred from this API's consistent `views`-per-result convention elsewhere, not yet directly confirmed. **Blog Followers** (`loadWordpressFollowers()` — avatar, name linking to their Jetpack profile, subscribed date; `subscribers[]`/`total_wpcom`/`total_email`/`pages`) only fetches page 1 (`type=wpcom`, no pagination wired up), though the summary line above the table always states the true `total_wpcom`/`total_email` counts regardless of how many pages exist. Data is fetched only once actually expanded, rather than on every Analytics page load.
- **GA4** (five sections): Top Pages, Traffic Sources, Device Category, Top Countries — fully formatted tables (`loadGA4Breakdown()`), each a single-dimension/single-metric `runReport` call (sorted desc, top 15) reusing the exact same response-parsing logic already verified against a real property for the daily-trend card above it. **AI Assistant Referrals — GEO** (`loadGA4AiReferrals()`) is the odd one out: there's no API for "how often an AI engine mentions this site" (Generative Engine Optimization proper would mean a separate tool periodically querying each AI service directly), so this instead surfaces the closest real, passive signal GA4 already has — actual sessions attributed to a `sessionSource` matching a curated list of known assistant domains (`GA4_AI_REFERRAL_DOMAINS`: chatgpt.com, chat.openai.com, perplexity.ai, gemini.google.com, bard.google.com, copilot.microsoft.com, claude.ai, you.com, poe.com, meta.ai). Fetches `sessionSource` at a wide `limit:200` (AI referral volume is typically too low to place in a default top-15) and filters client-side against that list rather than a server-side dimension filter, since GA4's API filters one dimension value/regex at a time, not "any of a domain list." Necessarily undercounts assistants that strip the referrer entirely (ChatGPT's mobile app, notably) — those sessions are indistinguishable from ordinary `(direct)` traffic, a limitation stated directly in the section's own hint text rather than left implicit. Data is fetched only once actually expanded.
- **Yoast** (two sections, **Posts** and **Pages** — `yoastSeoTableHtml()`): unlike WordPress/GA4's drill-downs, expanding either one doesn't trigger its own separate fetch — both types are already pulled together by the one `loadYoastSeoAudit()` call the summary tiles need anyway, so an expand just renders (or re-renders, since the section body isn't cached) that type's rows from data already in hand.
- **Mailchimp — Recent Campaigns** (`mailchimpCampaignsSectionHtml()`) is the one exception to "collapsed shows nothing": collapsed, it still shows a one-line summary of the single most-recently-sent campaign (subject, send date, emails sent, opens/open rate, clicks/click rate) via `loadLatestMailchimpCampaignSummary()`, so collapsing the full list never hides today's numbers. Expanded, `loadMailchimpCampaignsReport()` replaces that with a full table of the 10 most recent sent campaigns (`GET /reports?list_id=...&count=10`), each row clickable. Either the summary line or a table row opens `openMailchimpCampaignActivity()` — a per-recipient modal (`GET /reports/{id}/email-activity`) listing every recipient's Opens/Clicks counts and last-activity date, engaged recipients sorted first. The three `.mc-tile-to-campaigns` stat tiles on the main Mailchimp card (Campaigns Sent/Avg Open Rate/Avg Click Rate) jump straight to the expanded table rather than duplicating these same numbers in a second place.

## 4. Integrations

### 4.1 Google Drive Backup
"Backup to Google Drive" / "Restore from Google Drive" buttons (File menu, now grouped under a "Manual Fallback (not identity-verified)" label — see §4.1a). OAuth PKCE flow, token exchange/refresh proxied through `api/drive-token.js` (holds `GOOGLE_CLIENT_SECRET` server-side). Backs up the entire `db` object as one JSON file (`milesman-crm-backup.json`) via `driveBackup()`/`driveRestore()`, with the browser talking to the Drive API directly using its own access token.

**Multi-device conflict protection**: `mm_last_known_remote_modified` (localStorage) tracks the Drive file's `modifiedTime` as of this device's last successful backup or restore. Before any backup upload, `driveConflictDetected()` compares that against the file's *current* `modifiedTime` on Drive — if they differ, another device has backed up more recently, and the upload is blocked (with a toast telling the user to restore first) rather than silently overwriting newer data.

`DRIVE_SCOPE` includes `openid email` alongside `drive.file` — not used by this path at all, but every token exchange/refresh here also opportunistically returns and stores an `id_token` (`mm_drive_id_token`) purely so §4.1a's Secure Sync has a fresh one available without its own separate sign-in flow.

### 4.1a Secure Sync (server-verified alternative)
"Secure Sync: Save" / "Secure Sync: Load" (File menu, styled as the primary path, above the Manual Fallback group) — an additive alternative to §4.1, not a replacement; both read/write the exact same `milesman-crm-backup.json` file and can be used interchangeably. The difference is *who* decides whether the read/write happens:

- §4.1's buttons: the browser itself holds a Drive access token and talks to Drive directly — no server-side identity check beyond Google's own OAuth consent screen and `drive.file` scoping.
- Secure Sync: the browser sends a Google **ID token** (`mm_drive_id_token`, captured as a side effect of the §4.1 token flow — see above) to a new endpoint, `api/secure-sync.js`, on the `milesman-auth` Vercel proxy. That endpoint verifies the token against Google's `tokeninfo` endpoint (checks signature validity, audience, `email_verified`), checks the email against an `ALLOWED_EMAILS` allowlist, and only then uses its **own** stored Drive credential (`DRIVE_SERVER_REFRESH_TOKEN`, a one-time real OAuth grant from an allowed account) to read/write the backup file. The browser never holds a credential capable of reaching the data on this path.

Required Vercel env vars for `api/secure-sync.js` (in addition to the already-set `GOOGLE_CLIENT_SECRET`): `DRIVE_SERVER_REFRESH_TOKEN`, `ALLOWED_EMAILS` (comma-separated). Setup convenience: **Copy Drive Refresh Token** (Debug Panel area) copies this device's already-obtained `mm_drive_refresh` value to the clipboard for pasting into Vercel — no separate OAuth flow needed to stand up the server side, as long as Backup/Restore has been connected at least once already.

**This is real, not cosmetic**: unlike the password gate (§1), the verification here happens on a server the browser's own JS can't skip or edit. It narrows one specific gap — a third party with no access to an allowed Google account pulling the data over the network — but doesn't change anything about data already resident in a device's `localStorage`, and doesn't (yet) gate the app's own rendering/login, only this one sync path.

### 4.2 Outlook Email Sync
"Sync Outlook Emails" — OAuth PKCE against Microsoft Graph (`Mail.Read` scope). Fetches Inbox + Sent once per sync (`fetchMailbox()`), then matches it against three separate record types, each logging into its own `notesLog` (as `Email Sent`/`Email Received` notes, via the shared `emailToNote()`): every **client** with an email on file, every **Supplier Contact** (`allVendorContacts()` — `db.vendors[].contacts[]`), and every **Vendor Contact** (`allBizVendorContacts()` — `db.bizVendors[].contacts[]`). All three loops share the same match/dedup/append logic — only which array gets written back differs. Incremental after the first run via the `mm_last_outlook_sync` timestamp marker; "Reset Outlook Login" clears that marker to force a full resync. Pagination caps at 8,000 messages/folder per sync pass (`MAX_PAGES=80`, `$top=100`) — the Debug Panel logs a warning if a mailbox is too large to fully cover in one pass.

### 4.3 Mailchimp Activity Sync
Two related buttons:
- **Sync Mailchimp Activity** — fetches the single most-recently-sent Mailchimp campaign, then for each client checks (via the campaign activity-feed API, keyed by an MD5 hash of their lowercased email) whether they actually received it, and if so logs a `Mailchimp Email Sent` note with the campaign subject/body. Idempotent (a `mcKey` on each note prevents re-logging the same campaign for the same client).
- **Log Mailchimp Campaign** — a manual fallback: type in a subject/summary yourself and pick which clients to log it against, without hitting the Mailchimp API at all.

**Auto-subscribe on new clients**: `autoSyncSubscriberToMailchimp(client)` fires when a client is created with `isSubscriber` already checked (`saveClient()`'s new-client branch) or when the WordPress blog-follower sync (§4.3a) auto-adds a new subscriber. It upserts the client into whichever Mailchimp audience was last chosen (`MAILCHIMP_LIST_KEY`) via `status_if_new:'subscribed'` only — deliberately never overrides `status` on an existing member, so a background auto-add never silently re-subscribes someone who unsubscribed directly through Mailchimp. Silent no-op (debug log only) if no audience has ever been picked yet, since that just means Sync/Log Mailchimp Activity hasn't been used once to establish it.

**Real two-way push on the Sub checkbox**: toggling the Sub checkbox on the Clients page (or applying a row in the Sync Subscribers review, §4.3c) is a deliberate action, not a background guess — it calls `pushMailchimpSubscriberChange(client, status)`, which sets Mailchimp's `status` field explicitly (`subscribed` or `unsubscribed`), overriding whatever the member's current status was. This is what makes unsubscribing actually work: Mailchimp's unsubscribe endpoint (`PUT /lists/{id}/members/{md5(email)}` with `status:'unsubscribed'`) is standard and documented, so this is a genuine, real removal — unlike the Jetpack side below.

### 4.3a Jetpack Auto-Subscribe
Jetpack/WordPress.com has **no public, documented REST API** for adding an individual email subscriber — the `WP_SCOPE='stats'` OAuth connection used for the Analytics tab (§ below) is read-only, and Jetpack's own officially supported path is a manual CSV upload in WP Admin (Jetpack → Newsletter → Subscribers → Add Subscribers → Upload CSV).

To get a real automatic push instead, this app calls a small custom REST route installed directly on the WordPress site itself — see `wordpress-snippets/jetpack-subscribe-endpoint.php` in this repo for the PHP to install (via a plugin like "Code Snippets", or as an mu-plugin) plus full setup steps in its header comment. That route wraps Jetpack's own internal `Jetpack_Subscriptions::subscribe($email)` method (the same one Jetpack's subscribe widget/block uses — not a documented public API, so a future Jetpack update could rename/remove it) and is authenticated with a WordPress **Application Password** (Basic Auth), not the OAuth stats token, since it's a route this app's own snippet controls rather than a public WordPress.com endpoint.

- `getJetpackSubCreds()`/`promptJetpackSubSetup()`/`disconnectJetpackSub()` manage the WP username + Application Password (`mm_jetpack_sub_user`/`mm_jetpack_sub_pass` in localStorage) via the Analytics tab's WordPress.com / Jetpack card ("Set Up Auto-Subscribe" / "Change" / "Disconnect") — independent of that card's Stats OAuth connection, since the two use entirely different auth.
- `syncClientToJetpack(client)` POSTs `{email}` to `https://themilesman.com/wp-json/milesman/v1/subscribers` with `Authorization: Basic base64(user:apppass)`.
- `autoSyncSubscriberToJetpack(client)` is the fire-and-forget wrapper (debug log on success, toast only on a real failure — "not set up yet" is a silent expected state, same convention as the Mailchimp version) — called from `saveClient()`'s new-client-with-Subscriber-checked branch, the Sub checkbox toggle on the Clients page, and applying a "subscribe" row in the Sync Subscribers review (§4.3c).
- **Registering the subscription is not the same as it being active** — Jetpack still sends its own confirmation email to the address, and the person has to click it, exactly as if they'd used the subscribe widget by hand. There's no way to skip that step through this or any other integration path.

**Removal has no equivalent path — this is a real, confirmed capability gap, not an oversight.** Jetpack/WordPress.com has no documented API, public or internal, for removing a subscriber by email: `Jetpack_Subscriptions` (the class `jetpack-subscribe-endpoint.php` calls into) has `subscribe()` but no `unsubscribe()`/`remove()` method, and WordPress.com's REST API only exposes self-service per-account unsubscribe endpoints, not an admin-driven one keyed by arbitrary email. The only confirmed way to remove someone is by hand in WP Admin (Jetpack → Subscribers → the row's ⋯ menu → Remove).

So unlike Mailchimp, unchecking the Sub checkbox (or applying an "unsubscribe" row in the Sync Subscribers review) can't push a real removal to Jetpack — it calls `flagJetpackManualRemoval(client)` instead, which appends `{clientId, name, email, flaggedAt}` to `db.jetpackRemovalQueue` (skipped if that client is already queued). The queue is surfaced on the Analytics tab's WordPress.com / Jetpack card as a red "Needs Manual Removal in WordPress (N)" list, each row with a "Done" button (`clearJetpackRemovalFlag(clientId)`) to check it off once removed by hand, plus a link straight to the site's Jetpack admin page. The Clients page's "Sync Subscribers" button (§4.3c) also shows a red count badge whenever this queue is non-empty.

### 4.3c Subscriber Reconciliation ("Sync Subscribers")
The auto-push described above only catches changes made *in* the CRM. It can't catch someone unsubscribing directly through a Mailchimp email link, or being added/removed as a Jetpack follower outside the CRM. The **Sync Subscribers** button on the Clients page toolbar (`reconcileSubscribers()`) closes that gap — on demand, not automatically, and it never changes anything without the user reviewing and confirming first:

1. Requires at least one of Mailchimp (`MAILCHIMP_LIST_KEY` set) or WordPress/Jetpack (`mm_wp_token` set) to be connected; otherwise it just toasts asking to connect one first.
2. Pulls the current subscribed-member list from Mailchimp (`/lists/{id}/members?status=subscribed`) and/or the current email-follower list from Jetpack (`fetchAllWordpressFollowerPages(token,'email')`, the same call §4.7's blog-follower sync uses).
3. For every client with an email, compares `isSubscriber` against whichever of those two lists are available. A client where all known values agree is skipped; everyone else becomes a mismatch row.
4. If there are zero mismatches, it just toasts "All subscriber lists already match" and stops there — no modal, nothing to review.
5. Otherwise it opens a review modal (`openSubscriberReconcileModal`) — one row per mismatched client, showing a ✅/Not-sub badge for each connected source, and a per-row action dropdown (Mark Subscribed / Mark Unsubscribed / Skip) defaulting to whichever direction has *any* source saying "subscribed" (a deliberate bias toward not losing a subscriber by accident — the user can still override any row before applying).
6. **Apply** (`applySubscriberReconciliation`) only touches rows that aren't set to Skip: for "Mark Subscribed" it sets `isSubscriber=true`, force-pushes `subscribed` to Mailchimp, and pushes to Jetpack if not already a follower there; for "Mark Unsubscribed" it sets `isSubscriber=false`, force-pushes `unsubscribed` to Mailchimp, and — if the client was a Jetpack follower — queues them in the manual-removal queue above instead of pretending to remove them. Takes an undo snapshot first, same as every other bulk-write feature in the app.

### 4.4 Automatic Trip-Form Email Import
Every 5 minutes (and once ~5s after page load), while the CRM tab is open, `checkForNewTripFormEmails()` polls the same connected Outlook inbox for new emails matching `TRIPFORM_EMAIL_SUBJECT_RE` — a loose regex (`/^New submission\b.*\bBook a trip$/i`) rather than one exact literal string, since the notification service's exact wording between "New submission" and "Book a trip" has already changed once ("for" → "-") and silently broke matching entirely until diagnosed — and imports each one automatically — creating/enriching client records and a trip record exactly like the manual CSV import (§5's "Import pipeline" below shares the same `processTripFormRow()` logic). `checkForNewContactFormEmails()` (§4.5) runs on the same `setInterval`/`setTimeout` calls, so both checks fire together every 5 minutes.

**Important constraint**: this is *only* a foreground-tab poller, not a real background job — there is no server to run it when nobody has the CRM open. **This used to fail completely silently** (no log line at all) when Outlook wasn't connected — now it logs `skipped — Outlook not connected` (same fix applied to §4.5 and the revenue-report email check) so a lapsed connection is visible in the Debug Panel instead of a silent no-op. It also now logs how many messages were fetched and any near-miss subject matches, to make a future subject-wording change easier to diagnose than the incident above was.

**Parsing approach**: submit-form.com's notification email has no reliable delimiter between fields in its plain-text form — an unanswered field just runs straight into the next field's label with no separator. `parseTripFormEmailText()` works around this by building the complete set of every field label the intake form can possibly submit (`buildTripFormFieldLabels()`, mirroring intake-form.html's `name="..."` attributes exactly, including the dynamic per-brand balance-grid and per-traveler fields), finding every one that actually appears in a given email in one regex pass (longest labels matched first, so e.g. "Referred By" can't shadow "Referred By Detail"; word-boundary-guarded so short labels like "Airline" don't match mid-word inside typed text like "Alaska Airlines"), and taking each match's value as the text up to the next matched label. A separate pass swaps the literal token "Other" for a sentinel wherever a select-with-Other field's value is genuinely "Other" (to disambiguate it from the immediately-following "X Other" label's own text), then maps it back after matching.

Deduplication: processed message IDs are kept in `mm_tripform_processed_ids` (capped at 500) so the same email is never imported twice.

**Whenever a new field is added to the intake form, several places need updating** (all in index.html) or the new field silently won't reach the CRM from a real submission:
1. The `addLine(...)` call in `processTripFormRow()` (so it lands in the trip's notes).
2. The label list in `buildTripFormFieldLabels()` (so the email importer can find it — the manual CSV import path doesn't need this, only the automatic email path).
3. If the field should also become a structured trip field rather than just free-text notes — the `db.trips.push({...})` object itself (see `tripDepartDate`/`tripReturnDate`'s fallback chain for an example of a field feeding a structured column from more than one possible source).
4. If the field is a brand name that might match an existing Supplier record (an airline, hotel brand, cruise line, car rental company, theme park, or tour vendor) — add it to the `matchVendorByName(...)` calls near the bottom of `processTripFormRow()` so the client gets linked onto that supplier and it's eligible to become the trip's `supplierId`. This path never creates a new vendor, only links to ones that already exist, matching by exact case-insensitive name. (The Revenue importer's `extractRevenueRow`/`finalizeImport` used to follow this same never-create rule too, but now creates a missing Supplier on the fly — see the Suppliers section in §3 — since a revenue report's Name column is a much stronger signal that the text really is a supplier than a Book a Trip form's brand-preference fields are.)

**Companion travelers (Traveler 2+) get the exact same field set as the primary contact.** `travelerBlockHtml(n)` in `intake-form.html` and the `for(var tn=2; tn<=travelerCount; tn++)` loop in `processTripFormRow()` both cover Email/Phone/Street Address/City/State/Zip/Referred By/Referred By Detail/Discounts/Interests in addition to the Birthdate/Country/Preferred Airline-Hotel-Cruise/balance fields they already had — `referredByFieldGroupHtml()`/`discountsFieldGroupHtml()`/`interestsFieldGroupHtml()` in `intake-form.html` are shared builders used for both the primary contact's own fields and every Traveler N block, so the two field sets can't drift apart the way two hand-written copies eventually would (the primary contact's own static HTML for these three field groups was replaced with empty `display:contents` slots filled by the same builder functions at page load). The "Other" toggle wiring for these (a select/checkbox revealing a free-text detail field) is delegated by class (`.ref-select`/`.discount-other-cb`/`.interest-other-cb`) rather than per-instance ids, the same pattern `.pref-other-sel` already used, so it works for however many traveler blocks exist.

**Matching a companion traveler is still name-only** — the form collects no email for anyone but the primary contact, so first+last name (case-insensitive) is the only thing to match against `db.clients`. This is a real limitation: the form's own "Name as shown on passport or license" label actively invites a *legal* name, which can differ from whatever nickname an existing client is already filed under. A real incident this was built from: a submission's "Traveler 2 - Full Name" came in as "Jacqueline B Rogers," which didn't match an existing "Jakki Rogers" client record — the importer silently created a duplicate "Rogers, Jacqueline B" client instead of enriching the real one. Rather than continue silently duplicating (or loosen matching and risk silently merging two different people who share a surname), a companion traveler with **no exact match but at least one existing client sharing their last name** is queued to `db.pendingTravelerMatches` instead of being auto-created — see "Pending Traveler Matches" below. A traveler with no exact match and no same-last-name candidate either (genuinely nobody similar on file) is still created immediately, same as before; queuing only kicks in when there's an actual ambiguity worth a human's attention.

**Pending Traveler Matches** (`openPendingTravelerMatchesModal()`/`resolvePendingTravelerMatch()`, sidebar Import menu, `db.pendingTravelerMatches`) — the same queue-and-resolve-whenever shape §5's "Pending Import Matches" (`db.pendingImportMatches`) already used for unmatched Revenue import rows, reused here rather than re-invented: each pending entry holds everything the queued traveler's form answers/balances/checklists, plus which existing clients share their last name as a hint. The modal lists every pending entry with a searchable-by-typing `<select>` of every client, a **Match** button (merges the queued fields/balances/discounts/interests onto the picked client the same field-by-field way an exact match would have, then links that client onto the trip and rewrites the trip's "NEEDS REVIEW" note line to a normal "Traveling with:" line), a **+ Add as New Client** button (creates the client fresh, same fields, then resolves the same way), and a **Discard** button (drops the queue entry with a confirm prompt; the trip keeps its "NEEDS REVIEW" note as a historical record, but no client ever gets linked). The modal stays open and re-renders itself after each action so several can be worked through in one sitting, exactly like Pending Import Matches. Since the traveler's own trip doesn't exist yet at the point in `processTripFormRow()` where the ambiguity is detected (companion travelers are processed before the trip record is created), queued entries are held in a local `pendingMatches` array and only pushed into `db.pendingTravelerMatches` (with `tripId` filled in) once the trip's id is actually known, right after `db.trips.push(...)`.

### 4.5 Automatic Contact-Form Email Import
The website's general contact form (`themilesman.com`, unrelated to the Book a Trip form) emails a `New submission from Miles Man Contact Form` notification per submission, in the same flattened "Label Value Label Value..." layout but with a much smaller fixed field set: `first_name`, `last_name`, `email`, `phone`, `message`, followed by a `Submitted <time> - <date>` footer.

`checkForNewContactFormEmails()` polls for this subject on the same 5-minute cycle as §4.4 (folded into the same `setInterval`/`setTimeout` calls, not a separate timer) and turns every submission into a lead via `processContactFormRow()`:
- Creates or matches/enriches a client record (same email/name matching as the trip-form importer).
- Logs a `Lead` note (`noteType: 'Lead'`) with the inquiry text.
- Creates a follow-up Planner task (`completionNoteType: 'Lead'`).

`message` is deliberately excluded from the generic label-boundary scan (`parseContactFormEmailText()`) and instead runs to the end of the text once its label is found — an inquiry can easily contain the words "email" or "phone" ("please email me back"), which would otherwise be mistaken by the scan for the start of a later field and truncate the message. Deduplication mirrors §4.4: processed message IDs in `mm_contactform_processed_ids` (capped at 500).

### 4.6 Automatic Birthday-Trip Reminders
`checkForUpcomingBirthdays()` — folded into the same `setInterval`/`setTimeout` calls as §4.4/§4.5, but needs no Outlook connection (pure `db.clients` scan). ### 4.7 WordPress.com / Google Analytics (GA4) Stats
Two independent integrations powering the Analytics tab (§3) — see there for the user-facing page layout; this is the OAuth/proxy mechanics behind both.

**WordPress.com/Jetpack Stats** — a full OAuth2 Authorization Code flow (no PKCE, unlike Drive/Outlook — WordPress.com's flow is a traditional confidential-client one), against `WP_CLIENT_ID` (`145675`, hardcoded, not secret) and `WP_SCOPE` (`stats`). `wordpressLogin()` redirects to `https://public-api.wordpress.com/oauth2/authorize`; `checkWordpressRedirect()` (called unconditionally at boot, alongside `checkDriveRedirect()`) picks the returned `code` off the URL and exchanges it via `api/wordpress-token.js` on the `milesman-auth` Vercel proxy, which holds `WORDPRESS_CLIENT_SECRET` server-side. The resulting `access_token` is stored as `mm_wp_token` — WordPress.com's Authorization Code Grant response documents no `refresh_token`/`expires_in`, so unlike Drive there's no refresh path here; if a token ever stops working, the fix is just reconnecting.

Actual stats data (`loadWordpressStats()`/`loadWordpressExtra()`) is fetched through a *second*, secret-free proxy, `api/wordpress-stats.js` — public-api.wordpress.com sends no CORS headers on its REST API even for an authenticated request, so a direct browser fetch fails outright ("Failed to fetch") despite a perfectly valid token; this endpoint just relays whatever `path` query param and `Authorization` header the caller sends, adding CORS — the same `?path=` relay shape `api/mailchimp.js` already used, though for a different reason (there, keeping Mailchimp's static key server-side; here, purely CORS, since the token itself is already exposed to the browser).

**GA4** — deliberately reuses the *existing* Drive OAuth token rather than a separate login: `DRIVE_SCOPE` (§4.1) now includes `https://www.googleapis.com/auth/analytics.readonly` alongside `drive.file`/`openid email`, and `getDriveTokenSilent()` (§4.1's silent/non-redirecting token getter) backs the GA4 card too. Google's Analytics Data API (`analyticsdata.googleapis.com`) sends CORS headers fine, so unlike WordPress this needs no relay proxy — `loadGA4Stats()`/`loadGA4Breakdown()` call `POST /v1beta/properties/{GA4_PROPERTY_ID}:runReport` (`GA4_PROPERTY_ID` = `362931402`) directly from the browser with the Drive access token as the Bearer credential.

**Both cards' day-by-day tables collapse by default, but the most recent date stays visible either way.** `loadWordpressStats()`/`loadGA4Stats()` each compute a one-line "Most recent: `<date>` — …" summary from the same data before rendering the table, shown unconditionally above the toggle. The 30-day table itself sits behind `inlineCollapseHeaderHtml(key, title)`/`bindInlineCollapseToggle(key, containerEl)` (keys `wp-daily-table`/`ga4-daily-table`) — a lighter sibling of `analyticsSectionHtml()`/`analyticsSectionCollapsed()` (used everywhere else on this tab, e.g. Top Posts/Referrers) for the case where the data is already in hand rather than something to lazily fetch on expand, so it renders just the toggle header (no `Loading…` body div) and gates the already-built table markup on `analyticsSectionCollapsed(key)` directly. It also can't rely on the one-time delegated `.analytics-sec-hdr` click binding `renderAnalytics()` does for the other sections — that binding runs once against the tab's initial synchronous HTML, before these two cards' async `loadWordpressStats()`/`loadGA4Stats()` calls have replaced `wp-stats-body`/`ga4-stats-body` with their own markup — so `bindInlineCollapseToggle()` rebinds a fresh listener locally, inside each load function, every time that body is rewritten.

**The scope-widening gotcha**: adding a scope to `DRIVE_SCOPE` doesn't retroactively apply to an already-issued `mm_drive_token` — an old token still reads as "connected" (not expired) to `getDriveTokenSilent()`, so a missing-scope failure only ever shows up as a Google API error (`"Request had insufficient authentication scopes"`), never as "not connected." Both `loadGA4Stats()` and `loadGA4Breakdown()` pattern-match that specific error message and render a **Reconnect Google Drive** button in its place instead of the raw error — `driveLogin()`'s existing `prompt: 'consent'` param forces a fresh consent screen even for an already-authorized app, so re-clicking through it is enough to pick up the new scope. (Also required, separately, on Google's side: adding `analytics.readonly` under the OAuth consent screen's own configured-scopes list in Cloud Console — enabling an API and authorizing an OAuth app to actually *request* one of its scopes are two different settings, and only enabling the API isn't enough on its own.)

`driveLogin()` stages an optional `mm_drive_action` value in localStorage before redirecting (`'backup'`/`'restore'`/`'analytics'`), read back by `checkDriveRedirect()` after the token exchange to resume whatever the user was doing — `'analytics'` calls `go('analytics')` to land back on this tab. It only defaults this to `'pending'` when nothing more specific was already staged by the caller (a bug fixed alongside this feature — it used to overwrite any caller-set value unconditionally, silently dropping the Analytics tab's intent to return there after reconnecting).

**Blog Followers → Clients sync** — `syncBlogFollowersToClients(token)` runs automatically every time the Analytics tab renders with WordPress connected (alongside `loadWordpressStats()`), keeping the CRM's client list and every subscriber's checkbox in sync with WordPress.com's actual email subscriber list with no manual step. It calls `fetchAllWordpressFollowerPages(token, 'email')` (the `type=email` follower list — `type=wpcom` followers are anonymous WordPress.com usernames with no email field at all, so they're excluded from this matching entirely) and, per confirmed real-response field names, treats each subscriber's `label` field as their email address (there's no separate `email` field for this type). Each subscriber email is matched case-insensitively against `db.clients[].email`: a match gets `isSubscriber` flipped to `true` if it wasn't already; no match creates a new minimal client record (`name`/`email` = the subscriber's address, `isSubscriber: true`, `joined: today()`, a `notesLog` entry noting the auto-add). `snapshot()`/`saveDB()`/`toast()`/`render()` only fire lazily, on the first actual change — a run that finds everything already in sync makes no writes and shows no toast, which is also what keeps the automatic re-render from looping (the second pass finds nothing left to do).

### 4.8 Facebook Ads / Instagram (Marketing API)
Powers the Marketing tab (§3) and the Analytics tab's Facebook card (WordPress.com / Jetpack, Google Analytics (GA4), SEO (Yoast) — §3 Analytics). A full OAuth2 Authorization Code flow against `FB_APP_ID` (`1037570602213729`, hardcoded, not secret) and `FB_SCOPE` (`ads_management,ads_read,business_management,pages_show_list,pages_read_engagement,instagram_basic,instagram_manage_insights`). `facebookLogin()` redirects to `https://www.facebook.com/v21.0/dialog/oauth`; `checkFacebookRedirect()` (called unconditionally at boot, same pattern as `checkWordpressRedirect()`/`checkDriveRedirect()`) picks the returned `code` off the URL and exchanges it via `api/facebook.js` on the `milesman-auth` Vercel proxy, which holds `FACEBOOK_CLIENT_SECRET` server-side and chains a second call trading the short-lived token for a long-lived one (~60 days).

Actual Graph API calls (`fbGraph(path, opts)`) go through the same `api/facebook.js` — a CORS relay in the same `?path=` shape as `api/wordpress-stats.js`, forwarding whatever `Authorization` header and (for a POST, e.g. the Pause/Activate toggle or the campaign-creation wizard's sequential creates) JSON body the caller sends. `FB_AD_ACCOUNT` (`act_2429348457583319`) is the one ad account this integration targets. (`api/facebook.js` used to be two files, `api/facebook-token.js`/`api/facebook-graph.js`, merged for the same Vercel Hobby 12-Serverless-Function-cap reason `api/canva.js`/`api/x.js` are single files — see §4.10. Since Facebook's Graph relay needs POST too, the merged file can't distinguish the two halves by HTTP method the way `api/x.js` does; it routes on whether the request carries a `path` query param instead — token-exchange calls never send one, Graph relay calls always do.)

**Meta App Review gotcha**: an ad-account-scoped error like `"API Access Blocked"` almost always means the Facebook App hasn't been through Meta's App Review for the Marketing API permissions above, or the Business Manager owning `FB_AD_ACCOUNT` hasn't completed Business Verification — not a bug in this code. §3's Marketing section covers how the actual `code`/`error_subcode` gets logged to the Debug Panel to help pin down which. This app runs in Meta's **Development Mode**, not through full App Review — a real, previously-diagnosed failure mode of that (see the `FB_SCOPE` comment in `index.html`) is a scope that requires Advanced Access rejecting the *entire* login dialog with a "Feature Unavailable"/"Invalid Scopes" error rather than just that one permission being unavailable — `read_insights` did this and was permanently removed as a result. `instagram_basic`/`instagram_manage_insights` (added for Instagram analytics — see §3 Analytics) carry this same unconfirmed risk; if Facebook Connect ever starts failing with a scope error, those two are the first suspects to remove.

**Instagram** rides on this exact same connection — Meta requires an Instagram Business/Creator account to be linked to a Facebook Page, and serves its data through that Page's own access token rather than a separate login (`fetchInstagramAccountId()`: `/me/accounts?fields=...,instagram_business_account` finds the first connected Page with one linked). `followers_count`/`media_count` come from the IG account object itself (`GET /{ig-id}`); `reach`/`views`/`profile_views` come from `GET /{ig-id}/insights`, using the current (2025+) metric names — Meta deprecated the `impressions` metric across the whole Instagram Graph API in April 2025 in favor of `views`. `igInsightValue()` defensively reads either the newer `total_value` single-aggregate shape or the older `values:[{value}]` time-series shape per metric, since which one applies isn't consistently documented. None of this is confirmed against a live response yet, the same unconfirmed-shape caveat as the Ads/Page metrics above — a wrong guess shows Meta's real error message verbatim (`fbLogGraphError`) rather than failing silently.

### 4.9 Yoast SEO / WordPress Site REST Proxy
Powers the Analytics tab's SEO (Yoast) card (§3). Unlike every other integration in this section, this one needs **no OAuth token at all** — `yoast_head_json` (SEO title, meta description, robots directives, canonical, OG image, schema.org data) is attached to every post/page by Yoast SEO in the site's own public WordPress REST API (`https://themilesman.com/wp-json/wp/v2/posts`/`/pages`) by design, confirmed live (`curl`, no auth) before building anything on top of it.

The only reason a proxy exists here at all is CORS, not auth: self-hosted WordPress's REST API sends no `Access-Control-Allow-Origin` header, so a direct browser fetch from this CRM's GitHub Pages origin is blocked even though the data itself is already public. `api/wordpress-site-rest.js` (new endpoint on the `milesman-auth` Vercel proxy) is a bare CORS relay in the same `?path=` shape as `api/wordpress-stats.js`, but with the site domain (`themilesman.com`) hardcoded server-side rather than caller-supplied, so it can't be used as an open proxy to fetch arbitrary URLs — only `?path=` and its query string get forwarded, always against `https://themilesman.com/wp-json`. `loadYoastSeoAudit()` calls it twice in parallel (`/wp/v2/posts` and `/wp/v2/pages`, `per_page=100` each, `_fields=` trimmed to just what's needed) and merges both into one table.

WordPress's `title.rendered` comes back HTML-entity-encoded (e.g. `&#8211;` for an em dash) — passing that straight into `escHtml()` double-escapes it, showing the raw entity code instead of the character. `decodeHtmlEntities(str)` (a detached `<textarea>` — setting `innerHTML` on one never executes scripts, and reading back `.value` gives the decoded text) fixes this before `escHtml()` re-escapes the result for safe insertion.

### 4.10 X (Twitter) Analytics
Powers the Analytics tab's X card and the Dashboard's X Followers tile (§3). OAuth 2.0 **with PKCE** (mandatory for X, same as Canva — `xLogin()` reuses Canva's `canvaGenerateCodeVerifier()`/`canvaCodeChallenge()` helpers rather than duplicating that provider-agnostic math), authorizing at `https://x.com/i/oauth2/authorize` with scope `tweet.read users.read offline.access`. `checkXRedirect()` runs at boot alongside the other three redirect handlers. Access tokens last ~2 hours, so `getXAccessToken()` refreshes ahead of expiry exactly the way `getCanvaAccessToken()` does.

**This integration costs money per use, unlike every other one in this section.** X removed any usable free tier in February 2026 and moved to pay-per-use; a user-scoped read (which `/2/users/me` is) runs roughly **$0.010**. Two consequences are load-bearing in the design:

1. `xFollowerSnapshot(force)` caches one snapshot per calendar day in `localStorage` (`mm_x_follower_history`) and is the *only* path that calls X. Both the Dashboard tile and the Analytics card go through it, so a day of normal use — including navigating between those pages repeatedly — costs exactly one read, not one per render. **Do not "optimize" this into a fetch-on-render like the Instagram/WordPress follower tiles**; that would silently multiply a real bill. Only the explicit **Refresh now** button passes `force:true`. A *failed* read never writes a cache entry, so an error (e.g. no payment method on the X account) doesn't lock in a bad snapshot for the rest of the day.
2. The day-over-day follower delta (`xDeltaHtml()`/`xPreviousSnapshot()`) is derived from two cached snapshots rather than any API call, because X offers no account-level daily-insights endpoint the way Instagram does. `xPreviousSnapshot()` returns the most recent snapshot *strictly before* the current one — not necessarily literally yesterday, since a day the CRM was never opened records nothing — which is why the label names the actual comparison date ("+23 since Aug 21") instead of claiming "yesterday." Same discipline as the Mailchimp unsubscribe fix (§3's Mailchimp card): never label a number as a daily figure unless it genuinely is one.

**Required proxy endpoint** — doesn't exist yet in `milesman-auth`; checked into this repo at `vercel-endpoints/x.js` to be copied into that project and deployed (`vercel --prod`). One merged file rather than the two `index.html`'s own calling code implies (`/api/x-token`, `/api/x-api`) — `milesman-auth` is on Vercel's Hobby plan, capped at 12 Serverless Functions per deployment, and this project was already at that cap once before (the same reason `api/canva.js` is one file instead of the two it started as). A `vercel.json` `rewrites` entry maps both original paths onto this one function (`req.method` alone distinguishes the two behaviors inside it — token exchange is always POST, the API relay always GET), so `index.html` needed no changes:
- **Token exchange/refresh half** — holds `X_CLIENT_ID`/`X_CLIENT_SECRET` as Vercel env vars, and sends them as HTTP Basic auth, which X requires for confidential clients. The X Developer Portal app must be created as **"Web App, Automated App or Bot"** — a "Native App" is a public client with no secret and won't work with this endpoint.
- **API relay half** — CORS relay in the same `?path=` shape as `api/wordpress-stats.js`/`api/facebook.js`. Holds no secret (the browser's own user token passes through), but does allowlist read-only `/2/users/...`/`/2/tweets` paths so a borrowed token can't drive arbitrary billable or write calls through the proxy.

Deploying this one extra file tipped the live `milesman-auth` project's `api/` folder to 13 files — one over the Hobby cap even after the X merge, because several other endpoints in that folder had never been checked into this repo's `vercel-endpoints/` in the first place. `api/facebook-token.js`/`api/facebook-graph.js` were merged into `api/facebook.js` (see §4.8) to free the 13th slot back down to 12.

`X_CLIENT_ID` in `index.html` ships **blank** — until it's filled in from the Developer Portal, `xLogin()` refuses with an explanatory toast rather than bouncing the user to a broken X authorize URL.

### 4.11 TikTok Analytics
Powers the Analytics tab's TikTok card and the Dashboard's TikTok Followers tile (§3). Free — no per-request billing the way X is (§4.10). Plain OAuth2 Authorization Code flow, **no PKCE** — unlike X/Canva, TikTok only requires PKCE for desktop/iOS/Android (public clients that can't hold a secret); a web app whose secret stays server-side (here, in the proxy) is a confidential client and doesn't need it, so `tiktokLogin()` follows the same shape as `facebookLogin()`/WordPress's login rather than Canva/X's. **The `user.info.stats` scope name is an unconfirmed guess, not a verified one.** TikTok split `follower_count`/`following_count`/`likes_count`/`video_count` out of the base `user.info.basic` scope in a February 2024 migration, but the exact name of the replacement scope wasn't independently verifiable while building this (TikTok's own developer docs were unreachable from the environment this was built in). If the TikTok card shows a `scope_not_authorized` error, that's the first thing to check in the Developer Portal's actual available scope list — `tiktokUserInfoValue()` surfaces TikTok's real error message verbatim rather than failing silently, same discipline as the Instagram/Facebook metric-name uncertainty already documented in §4.8.

**Required proxy endpoint** — doesn't exist yet in `milesman-auth`; checked into this repo at `vercel-endpoints/tiktok.js` to be copied into that project and deployed. Deploying it requires a `vercel.json` rewrite mapping `/api/tiktok-token` and `/api/tiktok-api` onto `/api/tiktok`, the same shape as the X/Facebook rewrites in §4.10/§4.8.

Even merged into one file, adding TikTok tips the live `milesman-auth` project's `api/` folder to 13 files, since it was already at the 12-function cap after the X and Facebook merges — one more existing pair (`wordpress-token.js`/`wordpress-stats.js` is the obvious candidate, same token-exchange/CORS-relay shape) needs merging first to free the slot.

**Production access is gated behind TikTok's own App Review**, separate from the scope-naming issue above — a freshly-created app only works for "sandbox target users" explicitly whitelisted in the Developer Portal, not the real connected account, until TikTok approves the app's scopes for production (their own guidance: sandbox setup is hours, production review is typically days to weeks). **Daily Summary / "Yesterday's Analytics" block** (`fetchYesterdayTiktok()`, `dailyCompilationHtml()`, §3): the Display API's `/v2/user/info/` only ever returns current, all-time totals — there's no TikTok equivalent of Instagram's Insights endpoint offering a genuinely day-specific number. **Required proxy endpoints** — neither exists yet in `milesman-auth`; both are checked into this repo at `vercel-endpoints/` to be copied into that project and deployed (`vercel --prod`):

### 4.12 Credit Card Authorization Form Upload

[cc-auth-upload.html](cc-auth-upload.html) is a second standalone public page (same no-dependency-on-index.html shape as intake-form.html, §5) that lets a client securely upload their completed, signed credit card authorization PDF without logging in anywhere. Unlike every social/analytics integration above, there's no OAuth for the *client* here at all — the page is public, and the security boundary is entirely server-side.

**Two ways to reach this page**, both live at `cc-auth-upload.html`:
1. **Personalized per-client link**: on an existing client's record (Clients page — the button doesn't appear on a not-yet-saved client, since there's no id yet to embed), a **&#128274; Copy Upload Link** button next to Attachments builds `cc-auth-upload.html?cid=<id>&name=<name>` (`CC_AUTH_UPLOAD_URL` constant) and copies it to the clipboard (`navigator.clipboard.writeText`, same pattern as `copyDriveRefreshToken()`) for pasting into an email or text to the client. The page greets them by name and needs nothing further.
2. **Generic public link**: the bare URL with no query string at all — `https://milesmaneric.github.io/milesman-crm/cc-auth-upload.html` — meant to be posted as a static link on the website itself, for anyone to use without a CRM record existing first. Since there's no `cid`/`name` to read, the page instead shows two required fields, **Your Full Name** and **Your Email** (`#identify-fields`), and submits whatever's typed there as `clientName`/`clientEmail` in place of the personalized link's query-string values — this is what lets staff match an anonymous upload to a person afterward. Client-side, submit is blocked with an inline error until both are filled in; the server treats both link types identically (see "Security model" below) — the generic link isn't a lower-trust path, just a lower-information one.

**Upload flow**: the page validates client-side (must be `application/pdf`/`.pdf`, capped at 8MB — `MAX_BYTES` in both this file and the endpoint, kept in sync by hand) purely for a fast, friendly error message; none of that is trusted as the real security boundary. The file is read via `FileReader.readAsDataURL()`, base64-encoded, and POSTed as JSON (`{clientId, clientName, clientEmail, filename, fileBase64}` — `clientEmail` only ever populated from the generic link's identify fields; the personalized link's payload leaves it blank) to `https://milesman-auth.vercel.app/api/cc-auth-upload` — no multipart/form-data parsing needed server-side, matching this proxy's existing JSON-body convention (Secure Sync, the Claude relay) rather than adding a new dependency (`busboy`/`formidable`) just for this one endpoint.

**Server-side (`vercel-endpoints/cc-auth-upload.js`)**: re-validates everything the client already checked, since a malicious caller can trivially skip a browser entirely — decodes the base64, rejects anything over 8MB (413), and rejects anything whose first 4 bytes aren't the real `%PDF` magic bytes (400) before it ever reaches Drive. Then:
1. Mints a fresh Drive access token from the **same server-side credential Secure Sync (§4.1a) already established** — `GOOGLE_CLIENT_SECRET` + `DRIVE_SERVER_REFRESH_TOKEN`, both already set as Vercel env vars if Secure Sync is configured, no new secrets needed.
2. Resolves the upload folder (`getUploadFolderId()`) — and this step has a real, confirmed-against-a-live-account gotcha worth understanding. `drive.file` scope (§4.1) only grants a credential visibility into files/folders **it created itself** (or that were explicitly opened with it via a Picker) — never a folder the account owner made by hand in the Drive website, no matter its name or location. The very first version of this code searched for an existing **"Miles Man"** folder under Drive's root, found nothing (since it can't see the real, hand-created one), and silently created a brand-new **duplicate** "Miles Man" folder every cold start — Drive allows identically-named folders to coexist, so this surfaced as a second "Miles Man" folder (Drive's own UI disambiguates same-named siblings with a "(1)"/"(2)" suffix), not an error.

   The fix: `getUploadFolderId()` first calls `findFolderAnywhere()` — a lookup for a **"Credit Card Authorization Forms"** folder by name with **no parent constraint at all**, searching the whole set of folders this credential has ever touched, regardless of where they currently live. Since Drive's `drive.file` access is tied to a file's ID rather than its current parent, this makes a **one-time manual fix stick permanently**: drag the "Credit Card Authorization Forms" folder this credential created out of its own duplicate "Miles Man" folder and into the account's real one, delete the now-empty duplicate, and every future request finds that exact same folder (by ID) no matter where it was moved to — without ever needing to see the real "Miles Man" folder itself again. Only a genuine first run (no such folder exists anywhere this credential can see) falls back to creating a fresh **My Drive / Miles Man / Credit Card Authorization Forms** pair from scratch (`getOrCreateFolder()`, each level scoped to an explicit parent id).
3. Uploads the PDF into it via the same Drive `multipart` upload shape `driveBackup()` already uses client-side (`metadata` + `file` as two `FormData` parts), named `CC Auth - <client name> (<id>) - <ISO timestamp>.pdf` so it's identifiable without opening it. `<id>` is the real client id on a personalized link, falling back to whatever email the visitor typed in on a generic link (far more useful for matching than nothing at all), and finally to the literal text `no-id` if somehow neither is present.

**This never touches the CRM's own `db`/localStorage at all** — there's no automatic linking step. Once uploaded, staff review the PDF and attach it to the client's record the normal way, the same manual review step as any other Drive attachment. **Whether the CRM's own &#128193; Browse Google Drive... picker (the browser's own separate `drive.file`-scoped connection) can actually see a folder the server-side credential created is genuinely unconfirmed, and the folder-visibility gotcha above is a reason for real caution rather than optimism here** — if it doesn't show up there, reviewing directly in the Drive web UI (`drive.google.com`, under whichever account owns `DRIVE_SERVER_REFRESH_TOKEN`) always works regardless.

**Security model, spelled out**: this endpoint is deliberately public and unauthenticated — same trust level as the Book a Trip form (§4.4) and the Jetpack subscribe endpoint (§4.3a), not the allowlist-gated Secure Sync (§4.1a). A link (personalized or generic) grants upload-only access to one dedicated folder, never read access to anything; every upload is independently validated server-side regardless of what the client-side code claims — the generic link's identify fields are for staff matching, not an authentication check. There is no rate limiting or CAPTCHA — an accepted gap when this was only ever sent directly to known clients, but worth revisiting once the generic link is live on the public website, which will realistically see more random/automated traffic than a link only ever emailed or texted to someone by hand.

**Vercel body-size caveat**: `MAX_BYTES` (8MB) is a deliberately conservative guess, not a confirmed platform limit — Node.js Serverless Functions have historically capped request bodies well under that on some Vercel plans. If real uploads start failing with a `413` from Vercel itself (not this endpoint's own size check), lower `MAX_BYTES` in both files, or move to an Edge Function instead.

## 5. The Public Intake Form ("Book a Trip")

[intake-form.html](intake-form.html) is a standalone page with no dependency on index.html — it duplicates the constants it needs (`AIRLINES`, `HOTELS`, `CRUISE_LINES`, `CAR_RENTALS`, `CREDIT_CARDS`, `AIRLINE_CREDIT_CARDS`, `HOTEL_CREDIT_CARDS`, their status-tier maps, `SHIPS_BY_CRUISE_LINE`, cabin-type maps, the Transfers car-type list `Car/SUV/Van/Any` = CRM's `TRANSFER_CAR_TYPES`) so they must be **kept in sync by hand** whenever one file's list changes — there is no shared module.

### Structure
- **Your Information**: contact details, structured address, preferences (Airline/Hotel/Cruise Line, each with an "Other" free-text fallback), per-brand loyalty balance grids, and the Airline/Hotel Credit Cards checklists (`brandedCcChecklistHtml()` — plain checkboxes, one section per card, submitted as `name="<prefix> - <card name>" value="Yes"` only when checked). "Number of Travelers" dynamically renders additional traveler blocks (name, DOB, citizenship, preferences, balances, credit card checklists) for travelers 2+.
- **Trip Details**: a "Type of Travel Needed" checkbox row (Airline / Hotel / Tours / Cruise / Car Rental / Transfers / Car Service / Theme Park Tickets / Train / Bus) that each conditionally reveal their own detail section. **Destination** is a single always-visible field (not tied to any one checkbox, and not required) that sits above all of them, since it applies regardless of which service is needed.
  - **Airline Details** — departure/arrival city, dates, trip direction (+ dynamic multi-city stops), class of service (Basic Economy / Economy / Premium Economy / Business / First), a Non-Stop Flights Only yes/no question, and airline preference (with Other).
  - **Cruise Details** — cruise line (drives dependent Ship Name and Cabin Type dropdowns), nights, sailing date, departure port, cabin type, people in cabin, loyalty number, and — only when Cruise Line = Princess — a Cruisetour yes/no question. Cruise Line itself also has an Other free-text fallback.
  - **Hotel Details** — location, brand (with Other), a Check-in Date, nights, room type, people per room, number of rooms.
  - **Car Rental Details** — company (with Other), size, pickup/dropoff location, date, and time.
  - **Transfers / Car Service** — a dynamic "+ Add Another Ride" list (same add-row pattern as Multi-City Stops), one row per individual pickup: pickup date, pickup time, pick-up location, drop-off location, and a car-type preference (Car / SUV / Van / Any). Submitted as `Transfer N Pickup Date` / `Transfer N Pickup Time` / `Transfer N Origin` / `Transfer N Destination` / `Transfer N Car Type`; `processTripFormRow()` loops N=1..20 and writes one `Transfer N: <date time> | <origin> → <destination> | Car type: <type>` line into the trip's imported detail notes.
  - **Theme Park Details** — park (Disney World / Disneyland California / Universal Studios Hollywood / Universal Studios Orlando), and a multi-select ticket-type dropdown scoped to whichever park is chosen (each park has a different realistic ticket menu, e.g. Universal Orlando includes an Epic Universe standalone ticket and a 4-park hopper).
  - **Train** — departure/arrival city, departure/return date, and class of service (Coach / Business Class / First Class / Sleeper Car).
  - **Bus** — same fields as Train (departure/arrival city, departure/return date, class of service from the identical Coach / Business Class / First Class / Sleeper Car list), kept as a fully separate `booked.bus` category rather than folded into Train.
  - Tours Details (revealed by the Tours checkbox) also has a **Tour Vendor** pulldown (Tauck / Get Your Guide / Viator / Other) above the freeform description textarea.
  - Trip Type, Payment Preference, Notes, and a Trip Insurance yes/no question always appear, unconditional on the checkboxes above.

Every pulldown with an "Other" option (Airline, Hotel Brand, Cruise Line, Car Rental Company, Tour Vendor, and the "Your Information" preference selects) reveals a paired free-text input when "Other" is selected, via a shared `pref-other-sel`/`pref-other-wrap` class convention and one delegated `change` listener — adding a new "Other"-capable select just needs those two classes plus the paired wrap/input, no new JS.

**Depart date fallback for the Calendar**: the CRM's trip record needs *some* date to show up on the Calendar (`departDate`) and to sort correctly. Since Depart Date/Return Date only exist in Airline Details, `processTripFormRow()` falls back through `Depart Date → Sailing Date → Pickup Date → Transfer 1 Pickup Date → Hotel Check-in Date → Train Departure Date → Bus Departure Date` (and similarly for the return date) so a cruise-only, car-rental-only, hotel-only, train-only, or bus-only request still gets a usable date.

### Multi-select flattening
The Ticket Type field is a real `<select multiple>`. Since a browser would otherwise submit one `Theme Park Ticket Type` entry per chosen option, the custom submit handler collapses the selections into a single comma-joined string before sending — so the importer's one-value-per-field assumption holds without any special-casing downstream.

### Auto-resizing iframe
When embedded via `<iframe>` (as it is on the WordPress page), a fixed pixel height goes stale the instant a field is added or the page reflows for a different viewport width — silently clipping the bottom of the form, including the submit button. The page reports its real height to `window.parent` via `postMessage` (`ResizeObserver` + `MutationObserver` + a 1s poll fallback, since a parent-driven width change reflows content without firing either of those inside the frame). The **embedding page** needs a matching listener to actually resize the iframe element — see the snippet at the bottom of this section.

```html
<iframe id="milesman-intake-frame" src="https://milesmaneric.github.io/milesman-crm/intake-form.html" style="width:100%;height:2600px;border:none;"></iframe>
<script>
window.addEventListener('message', function(e){
  if (e.data && e.data.type === 'milesman-intake-height') {
    document.getElementById('milesman-intake-frame').style.height = e.data.height + 'px';
  }
});
</script>
```

### Import pipeline
1. **Manual**: submit-form.com's dashboard exports submissions as CSV. "Import" in the CRM (`importFormspreeSubmissions()`) reads the CSV and, for each row, calls the shared `processTripFormRow(getVal, counters)`.
2. **Automatic**: §4.4 above — same `processTripFormRow()`, fed from a parsed notification email instead of a CSV row.

Either path: matches/creates the primary client (by email, then exact name, then first+last name), matches/creates a client for every additional traveler (linked via the trip's `clientIds`), matches the requested Airline/Cruise Line/Hotel Brand/Car Rental Company/Theme Park/Tour Vendor against existing Supplier records by exact name (linking the client onto every match, and setting the first match in that priority order as the trip's `supplierId`/`supplierName` — never creates a new vendor), creates the trip record (`status: 'Planning'`), and creates a Planner follow-up task linked back to the trip. Loyalty balances (`mergeBalanceObjects()`/`mergeCreditCardBalances()`) and the `airlineCreditCards`/`hotelCreditCards` checklists (per traveler) get pulled in and merged — `extractCardChecklist()`/`mergeCardChecklist()` mirror `extractBalances()`/`mergeBalanceObjects()`, just checking checkbox presence instead of a number+status pair — and `buildTripFormFieldLabels()` includes every `AIRLINE_CREDIT_CARDS`/`HOTEL_CREDIT_CARDS` field label so the email-body parser (§4.4) recognizes them too.

**Plain-field merge direction**: every scalar field on an existing client (email, phone, street address, city, state, zip, birthdate, country of citizenship/birth, Referred By/Referred By Detail, preferred airline/hotel/cruise line, discountOther, interestOther) follows the same rule — `if(newValue && newValue!==client.existingValue)` — a present value on the new submission that's different from what's on file updates the record, since the client's own latest self-report is trusted over a possibly-stale existing value, but a field left blank on this particular submission never overwrites or clears an existing value. This used to be a narrower `if(newValue && !client.existingValue)` (fill-only-if-currently-blank, never update an already-populated field even to a corrected value) — companion travelers (Traveler 2+, same file) and the legacy PDF importer (`importTripFormPDF()`) had their own duplicate copies of this same narrower guard and got the identical fix. Checklist-shaped fields (`airlineCreditCards`/`hotelCreditCards`/`discounts`/`interests`) are deliberately exempt from this differs-then-replace rule — they stay a `mergeCardChecklist()` union (only ever adds, never removes), since an unchecked box on a resubmission means "not repeated here," not "no longer true," and replacing the whole set on any difference would silently un-know already-confirmed cards/discounts/interests the client just didn't re-check this time.

**Balance merge direction**: for an existing client, a nonzero balance on the new form submission always overwrites whatever was already on file for that program — a fresh self-reported number is trusted over a possibly-stale one already in the CRM — and likewise a status picked on the new submission overwrites the existing status. A program the client left entirely blank/zero on this particular submission is left alone entirely rather than treated as "now zero," so re-submitting the form without re-typing every balance doesn't wipe out real numbers the client just didn't repeat. `extractBalances()` already excludes an entry from the submission entirely unless it has a nonzero balance *or* a status, so a genuinely blank field never reaches the merge step to begin with.

The overwrite is now field-level, not wholesale: `mergeBalanceObjects()` used to replace the *entire* `{balance,status}` entry with whatever came in on the new submission, so a client who re-submitted with an updated balance but an untouched (blank) status dropdown had their real, previously-recorded status silently erased — the same bug pattern the user-facing "don't overwrite a field with no data" expectation calls out. It now keeps each existing sub-field whenever the incoming submission didn't provide that particular one (`incoming.balance ? incoming.balance : existing.balance`, independently for `status`), so a balance-only or status-only resubmission only ever touches the sub-field it actually carried data for. This same shared merge logic is also used by the legacy PDF importer (`importTripFormPDF()`), since it's processing the same kind of submission through an older delivery channel.

## 6. Debug Panel

A hidden diagnostic log (`debugLog(msg)`, persisted to `localStorage['mm_debug_log']`) used throughout the Outlook sync, Mailchimp sync, Drive backup, and auto-import features to record what happened on each run — request counts, pagination truncation warnings, per-client match counts, errors. This is the first place to look when a sync "did nothing" or produced unexpected results.

## 7. Known Limitations

- **No true backend.** Everything described as "automatic" (email polling, backups) only runs while a browser tab has the page open. There is no cron job, no server-side worker.
- **Two independent copies of shared constants** (airline/hotel/cruise-line lists, status tiers, ship/cabin-type maps) between index.html and intake-form.html. A brand added to one must be manually added to the other, plus any hardcoded `<option>` lists that aren't driven by the JS arrays (the "Preferred X" and top-level "Airline"/"Hotel Brand" selects are hardcoded; balance grids and per-traveler blocks are array-driven).
- **`localStorage` is the only live datastore** — clearing browser data with no recent Drive backup loses everything.
- **Aggressive host/CDN caching has bitten this project before**: the WordPress-embedded form was once observed being served with a 31-day `Cache-Control` header, meaning code fixes could take up to a month to reach real visitors until the cache was purged. Worth checking response headers directly (`fetch(url, {cache:'no-store'})`) whenever "I pushed a fix but nothing changed" comes up for the WordPress-embedded page specifically.
- **Supplier auto-linking is exact-name-only, never fuzzy.** A form submission's Airline/Hotel Brand/Cruise Line/Car Rental Company/Theme Park/Tour Vendor only links to a Supplier record whose `name` matches character-for-character (case-insensitive). A vendor named "Delta Air Lines" won't match a submission for "Delta" — keep Supplier names matching the exact option text used on the intake form.
- **No true submissions API for the intake form.** submit-form.com (the form backend) doesn't expose a polling API for raw submission data, only a dashboard/CSV export and webhooks — the CRM's automatic import stays email-based (§4.4) rather than polling submissions directly, since a webhook would need a server to receive it and this app doesn't have one.
- **The password gate (§1) is a casual deterrent, not real security.** The repo is public, so the check's own logic and the `localStorage` data it guards are both readable by anyone who looks — it only stops someone who stumbles on the URL from seeing data at a glance. Secure Sync (§4.1a) is the one path with actual server-side verification, and it's additive/optional, not the default gate on the app itself.
- **Generic loyalty tiers for the three newest cruise lines.** `CRUISE_STATUS['Explora Journeys']`, `['Seabourn']`, and `['Ritz Carlton Yachts']` are all a placeholder `['Silver','Gold','Platinum']` — their actual program tier names (if any) weren't confirmed before adding them; "Other" + free text still covers anything specific a client actually has.
- **Exact-string-matching email subjects are fragile against upstream wording changes** — this already happened once for the trip-form notification subject (§4.4) and went undetected for a while because the old code logged nothing when zero messages matched. The regex fix and added diagnostic logging reduce the *silent* half of this risk, but an exact-match subject constant could still need updating again if a notification service changes its wording.
- **The SEO (Yoast) Analytics card (§3/§4.9) can't show Yoast's own internal SEO/readability score.** That green/amber/red traffic-light score is derived from post meta (`_yoast_wpseo_linkdex`/`_yoast_wpseo_content_score`) only ever exposed to an authenticated wp-admin session — the public REST API `yoast_head_json` field this card reads has no equivalent. The card audits the same underlying signals (title/description length, noindex, missing OG image) instead, which is useful but not identical to what Yoast itself would show.
- **Facebook Ads (§3/§4.8) requires Meta App Review to fully work.** Without Advanced Access granted for `ads_management`/`ads_read` (and Business Verification for the Business Manager owning the ad account), Graph API calls return errors like `"API Access Blocked"` regardless of anything in this codebase — this is a Meta-side app/account configuration state, not something fixable in index.html.
